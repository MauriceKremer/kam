Feature Manual

MeshCore Room Server

Run a bulletin board on your mesh that stock MeshCore apps and radios can log in to.

Implemented (phases 1-3) Hardware verification pending Requirements and decisions: docs/FeatureRoomServer.md

Overview

A Room Server is a MeshCore node type (advert type ROOM) that works as a shared bulletin board. Clients log in with a password, post messages, and the server stores them and later pushes them to clients, including ones that were offline when the post was made. A room is different from a channel (group text): a channel is a shared-key broadcast that only people online at that moment see, while a room has its own identity and access control and keeps a history.

Key concept: think of a digital message board. Users log in to the board, leave messages, and when they come back online the board pushes them what they missed, one message at a time.

Example. You run KAM at a hilltop site and add a room called "KAM Lobby". A hiker with the MeshCore app imports the room, logs in with the guest password and posts "Trail closed at the ridge". Ten minutes later a second hiker, who was out of range, logs in. KAM pushes the post to that hiker's app. Both posts survive a KAM restart.

This manual describes the behaviour of MeshCore's reference room server (firmware v1.17.1, source commit a366955, 2026-09-30) because a stock MeshCore app must be able to use KAM's room. Where KAM deliberately differs, the text says so.

Terminology

To understand how Room Servers function, it is important to know these terms:

Term Definition
RoomThe post history of one room server. One identity is one room. (This is the MeshCore meaning; KAM does not mirror its group-text channels into rooms.)
ClientA MeshCore node (a radio or phone app) that has successfully logged in to the room.
PostA text stored by the room with the author's public key and a timestamp assigned by the server.
PushThe server sending one stored post to one client, then waiting for that client's ACK.
ACKA 4-byte acknowledgement. The server sends one for each accepted post; the client sends one for each push.
Sync cursor (sync_since)A per-client timestamp bookmark. Posts newer than it are still owed to that client.
Out pathThe stored direct route from the server to a client. If it is unknown, the server uses a flood (broadcast) instead.
AdvertA signed announcement that a node exists. A room's advert has type ROOM.
Public key / identityThe room's address, a 32-byte Ed25519 key. KAM stores the secret part in a key file; losing it changes the room's address.
Scope / regionA namespace on flood packets (transport codes) that lets repeaters limit where a flood travels.
RoleWhat a logged-in client may do: GUEST 0, READ_ONLY 1, READ_WRITE 2, ADMIN 3.
YAMLThe plain-text format of kam.yml, KAM's configuration file.

Setting Up a Room

Prerequisites. KAM already runs with its radio connected (see the KAM Guide), you can edit kam.yml on the host computer, and you have a MeshCore app or radio to test with. All commands below run in the KAM directory on the host.

1. Add the room to kam.yml

Add a rooms: list. The optional mesh: block sets radio-wide choices; default_scope should name the region your local repeaters expect, because repeaters may drop floods that carry no region.

mesh:
  default_scope: "#region"     # leave out to send unscoped floods
  duty_cycle_percent: 10       # airtime cap for pushes and adverts, 0 = off
rooms:
  - id: lobby
    name: "KAM Lobby"
    admin_password: "change-me-now"
    guest_password: "letmein"      # read-write
    allow_read_only: false         # true lets any other password log in as a guest

Passwords go in kam.yml as plain text, the same as channel keys.

Rules KAM checks when it starts: the id uses lowercase letters, digits, - or _; the name is at most 31 bytes (23 with a location); the admin password is required, at most 15 bytes and not password; a guest password and open_room cannot be combined. A room that breaks a rule is reported in the log and stays off; your other rooms and the radio keep working.

2. Print the room's key and advert

./kam room show
./kam room show -config ~/kam-prod.yml -db /var/lib/kam/kam.db

The command creates the room's identity key if it does not exist yet, then prints (long values shortened here):

Room lobby ("KAM Lobby")
  public key : 8a88e3dd...5c6f
  hash       : 8a
  key file   : rooms/lobby.key (created now; back it up, it is the room's address)
  contact URI: meshcore://contact/add?name=KAM+Lobby&public_key=8a88e3dd...5c6f&type=3
  advert hex : 10...

The key file is a single line of hex in a rooms directory next to the database. The public key is safe to share; the key file is not.

3. Start KAM and import the room

./kam

The log shows the room's public key and room ready. KAM sends one advert at start-up. In the MeshCore app, import the room with the contact link or QR code (the app understands meshcore://contact/add links), or wait for the app to hear the advert. Then log in with one of the passwords and post a test message.

4. Back up the identity

Copy the rooms directory together with kam.db. If you restore the database without the key, KAM creates a new key, the room gets a new address, and clients must import it again (the log warns: identity differs from the one stored).

How it Works

The interaction follows a specific lifecycle:

1. Discovery

The room announces itself with a signed ROOM advert containing its public key, name and optionally location. KAM sends a flood advert at start-up (in the default scope), a zero-hop advert every 2 minutes and a flooded one every 47 hours, all configurable; several rooms start 2 seconds apart. A client does not log in automatically when it hears an advert. Whether the app adds the room as a contact depends on its own policy and hop limit, and importing the contact link is the fallback. Clients ignore an advert whose timestamp is not newer than the last one they stored for that room.

2. Login

The client sends an encrypted Login Request (an anonymous request that carries its own public key) containing its clock, its sync cursor and a password. The server decides:

ConditionOutcome
Blank password from a client the server already knowsAccepted without re-checking; cursor, pending push, failures and route are left alone.
Password equals the admin passwordLogged in as ADMIN.
Password equals the guest password (or blank on an open room)Logged in as READ_WRITE (despite the name, this is the posting role).
Anything else, and allow_read_only is onLogged in as GUEST.
Anything else, and allow_read_only is offNo response at all. The client simply times out; the server never says "wrong password".
New login with a timestamp not newer than the last one from that clientDropped as a replay.
Too many attempts from one key (more than 5 quickly, then one every 2 seconds) or from all keys togetherDropped without any work, so password guessing over the radio stays slow.

On success the server stores the client's cursor, clears any pending push and failure count, remembers the shared secret, and waits 2 seconds before its first push. It answers with a small Login Response (server time, role and permissions, a random value and a firmware level) about 300 ms later.

3. Posting a message

A client sends a text message to the server. The server drops replays, checks the client's role, stores the post and, only after the post is durably stored, sends an ACK about 200 ms later. If the write fails, KAM sends no ACK and the client simply retries. A retry with the same client timestamp is acknowledged again but not stored twice. A GUEST post is not accepted and gets no ACK. Post text is limited to 150 bytes. An empty post is acknowledged but not stored.

4. Receiving pushes (catching up)

The server walks through its clients in turn. For a client that is due, it pushes the oldest post newer than the client's cursor (never the client's own posts, and only if the post is at least 6 seconds old). The client must acknowledge each push before the server sends the next to that client, which keeps the radio link from being flooded. A matching ACK moves the cursor forward. A missing ACK counts as a failure; after 3 failures the server stops pushing to that client until the client shows activity again.

Routes and paths

Replies travel either direct along a stored out path or as a flood. When a client receives a flooded packet from the server, it sends back a short PATH packet that carries the route it saw, and the server remembers that route as the client's out path. A flooded login or request is answered with a path return so the client learns the route; the server never sends a reciprocal path back. After three failed pushes KAM also forgets the route, so the next exchange finds a fresh one.

Keep-alive and other requests

Clients may send small requests (REQ): 0x01 status, 0x02 keep-alive, 0x03 telemetry, 0x05 access list (admin). KAM answers keep-alive only. Keep-alive works on direct routes. It refreshes the client's activity, may force the sync cursor, clears a pending push, and replies with an ACK plus a one-byte count of posts still owed. The other request types get no reply; KAM counts them. Any authenticated message or request from a client resets its failure count.

Cryptography

Room traffic between a client and the server is encrypted. These are MeshCore's protocol choices; KAM matches them exactly to interoperate.

  • Identity: each room has an Ed25519 key pair. The 32-byte public key is the room's address, and its first byte (the "node hash") is what packets carry. Keys starting with 0x00 or 0xFF are not allowed, and KAM avoids giving two of its rooms the same first byte.
  • Shared secret: client and server each compute the same 32-byte secret from their own private key and the other's public key (an X25519 key exchange derived from the Ed25519 keys). The secret itself is never transmitted.
  • Encryption: AES-128 using the first 16 bytes of the secret, in ECB mode with zero padding to 16-byte blocks. That is how the reference firmware works, so KAM does the same.
  • Integrity: a MAC of HMAC-SHA-256 over the ciphertext (keyed with all 32 secret bytes) cut to its first 2 bytes. The wire form is MAC | ciphertext.
  • Not everything is encrypted: adverts are signed, not encrypted, so anyone can read a room's name and public key. ACKs are a bare 4-byte hash. Packet headers, route and path are visible.

KAM holds each room's identity itself and does the signing and key exchange in software (the modem cannot be given a chosen identity). The key exchange is checked against a test key pair taken from MeshCore's own source, so a MeshCore client computes the same secret. Only the 32-byte seed is stored, as hex, in the room's key file.

Roles & Permissions

Once logged in, a client has a role. Login itself only hands out three of the four roles: the admin password gives ADMIN, the guest password gives READ_WRITE, and allow_read_only gives GUEST. READ_ONLY exists in the protocol but cannot be assigned by logging in; today KAM has no way to assign it, because role changes need the management API.

Role Reference firmware KAM
GUEST (0) Receives pushes. Cannot post: a post gets no ACK. Same.
READ_ONLY (1) Can post. The firmware only blocks role 0, so despite the name this role posts. Cannot post. KAM enforces the intended meaning.
READ_WRITE (2) Reads and posts. Reads and posts.
ADMIN (3) Reads and posts, can request the access list, and can send CLI commands over the air. Reads and posts, and is never evicted from the client table. Access-list requests and over-the-air commands get no reply.
Open rooms: with a blank guest password the reference firmware lets anyone log in as READ_WRITE. KAM only allows that if you explicitly set open_room: true.

The budget keeps your own node polite, but the air in your area is shared with every other node. KAMmon, the companion dashboard, shows your observed airtime; use it to watch how much of the hour your node is transmitting, and tune duty_cycle_percent, advert intervals and the number of rooms so your node does not crowd the network around you. The cap automatically holds back pushes and adverts, but you choose the settings that keep the shared channel free for others.

How KAM Differs from the Reference Firmware

Goals: a stock MeshCore client can discover or import the room, log in, post, receive pushes and reconnect and catch up; acknowledged posts survive restarts and power loss; room traffic cannot starve KAM's other functions; and an operator can run the room without an over-the-air command line.

Give the host a trustworthy clock. Clients use timestamps for replay checks and cursors. If KAM's clock steps backwards across a restart (a Raspberry Pi without a battery-backed clock or network time can), clients will ignore the room's adverts as "not newer" and will never receive new posts whose timestamp is below their stored cursor. KAM cannot see either failure. Within one run, post and advert timestamps always increase. KAM only logs a warning at start-up if the clock is earlier than the newest stored post.

Operating a Room

  • What the log shows: at start-up, one room identity line per room (public key, hash, key file) and room ready with the number of cached posts and restored clients. During operation: login accepted, login refused, login attempt rate limited, push not acknowledged, and errors such as post not stored. Passwords and full client keys are never logged; keys appear as their first 4 bytes.
  • Statistics: logins (ok, failed, rate-limited, replayed), posts (accepted, rejected), pushes (sent, acknowledged, timed out), unsupported requests and dropped packets are counted. KAM logs a summary when it stops; there is no export yet.
  • Changing a room: edit kam.yml and restart KAM. Changing the name or location changes the advert; clients keep the old name until they hear the new advert.
  • Removing a room: set enabled: false or delete the entry. The posts stay in kam.db and the key stays in rooms/, so re-enabling the same id brings the room back at the same address.
  • Isolation: a room failure never stops radio ingestion. A room that cannot start is logged and skipped.
  • Shutdown: KAM stops listening, then stops automation and the rooms (writing client sessions), then stops transmitting, then stops the modem manager.
  • Backups: keep kam.db (posts and sessions) and the rooms directory (identities). See the KAM Guide for how to copy the database safely.
  • Authentication: the Local Management API has none, so only loopback access protects it. Management of rooms through that API is planned, not available.

Technical Deep Dive

Note: This section contains implementation details intended for developers.

The Push State Machine

The server manages pushes through a state machine (diagram under How it Works) to stay reliable over unreliable radio links:

  1. Idle: a client is eligible when it has no push pending, has been active in this run, and has fewer than 3 failures. After a push the next scan is 1200 ms away, otherwise 150 ms.
  2. Choosing a post: the oldest cached post newer than the cursor, not authored by that client, at least 6 s old. The cache holds the newest backlog_posts posts, so a returning client is never sent more than that.
  3. Awaiting ACK: the push plaintext is post_timestamp(4) | text-type and random attempt bits(1) | author key prefix(4) | text. The expected ACK, SHA-256(push plaintext | client public key)[0:4], is recorded when the push is queued. The random bits make each retry's packet hash and ACK different.
  4. On match: the ACK may arrive as an ACK packet, a multipart ACK or inside a PATH. The server clears the pending push and failures and sets the cursor to the pushed post.
  5. On timeout: failures go up by one. At 3, the client is "starved" and gets nothing until it shows authenticated activity, and a stored route is dropped. The route is direct when an out path is known (timeout 4 s + 2 s × (hops + 1)) and otherwise a scoped flood (12 s). A push that is still waiting in the transmit queue at its timeout (for example held back by the airtime cap) is withdrawn without counting as a failure.

The push engine takes an injectable clock, so the tests run it deterministically.

Payload & Path Encoding

A packet is header | [transport codes(4)] | path_len | path | payload. In path_len, bits 0-5 are the hop count and bits 6-7 the hash size minus one; the value 0b11 is invalid. The path is at most 64 bytes and the payload at most 184. The router drops anything that breaks these rules.

Peer messages (request, response, text, path) are dest_hash(1) | src_hash(1) | MAC(2) | ciphertext. An anonymous request instead carries the sender's full 32-byte public key. One-byte hashes collide, so the server matches dest_hash to its own first key byte and then tries every known client with that src_hash until a MAC verifies. With several rooms, every room whose hash matches is tried.

The duplicate key is SHA-256(payload type | payload) cut to 8 bytes; the path is excluded. KAM remembers up to 512 keys for 2 minutes, and marks the room packets it transmits so a repeater's echo is ignored. A direct packet with a non-empty remaining path belongs to a forwarder, not to the final destination, so KAM ignores it unless it is an ACK. Flood packets are always processed. KAM never forwards.

Login response plaintext is 13 bytes: server time(4), login-OK flag, legacy keep-alive byte, admin/guest indicator, permissions, random(4), firmware level. For a flooded request it is wrapped in a PATH return (extra type RESPONSE); the combined path and extra data must stay within 166 bytes. Replies mirror the request's path hash size.

Scope: a scoped flood sets transport_codes[0] to the first 2 bytes of HMAC-SHA-256(region key, payload type | payload) read as a little-endian number (0x0000 becomes 0x0001 and 0xFFFF becomes 0xFFFE). The region key of a public region is the first 16 bytes of SHA-256("#" + name). A reply reuses the request's scope if it matches a configured region; an unscoped flood request gets an unscoped reply; otherwise the default scope is used if set. Repeaters may drop unscoped floods, so an unscoped reply may not travel.

Data Persistence

Rooms live in SQLite on a dedicated connection with synchronous=FULL and versioned migrations. The tables are rooms (id and public key), room_posts (room, server timestamp, author key, text) and room_clients (role, cursor, replay timestamp, route), all keyed by room id. Posts use a transactional, ordered store, not the batched drop-on-full queues that adverts and group texts use.

For every post KAM follows a "commit-before-ACK" rule: the message and the author's replay timestamp are written in one transaction before the confirmation is queued, so an acknowledged post survives a power loss. Post timestamps are strictly increasing, unique second values within a run (bumped by one when the clock repeats); if a stored post already has the timestamp after a clock step, the next free one is used. Retention pruning runs every 10 minutes. Client sessions are written in batches every 5 seconds and at shutdown.

Transmission

One transmit scheduler owns the radio data path for every producer (group-text sends, automation replies, rooms). It validates each packet, hands the modem one data frame at a time and waits for TxDone (or the writer's report that it gave up), with a timeout as a fallback. Priorities, highest first: direct ACKs and replies; flood replies and PATH; group texts; pushes; adverts. It supports the 200 ms ACK delay and 300 ms response delay and can cancel a queued push when it becomes obsolete.

Pushes and adverts are deferrable: when the estimated airtime of the last hour plus the next packet would exceed duty_cycle_percent, they wait. The estimate uses the LoRa airtime formula with an 8-symbol preamble; the modem's own airtime command is not used yet, so the real figure may be somewhat higher. The queue holds 128 packets; when it is full a deferrable packet is refused and an ACK evicts the newest deferrable one.

The modem's TXDELAY defaults to 500 ms (radio.csma.txdelay_ms). That latency may exceed client ACK timeouts, which firmware derives from estimated airtime, so measure it on hardware.
