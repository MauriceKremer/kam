The Story of KAM

The name KAM stands for KickAss Meshcore. This project was born from a single, driving question: how do we take the raw, unbridled energy of a MeshCore radio network and turn it into a structured, intelligent, and permanent foundation for community communication?

The spark for KAM came during the 2026 "May Month Meshcore Month." As the community rallied to build regional coverage, it became obvious that there was a gap in the tools available to enthusiasts. Maurice Kremer, a member of Hackerspace Drenthe, saw an opportunity to fill that gap with a tool that could act as a reliable room server and monitoring companion—helping to build the regional emergency backbone that MeshCore is capable of providing.

While MeshCore handles the "magic" of moving packets through the air, it is ephemeral by nature. KAM is the "brain" that catches those signals, gives them a memory through SQLite, and provides the muscle for automation via Starlark. We didn't just want a driver; we wanted to make MeshCore truly KickAss.

Just a heads up: KAM was born in Hackerspace Drenthe, but it's an independent project and doesn't represent the hackerspace officially.

What KAM Is

KAM is software that runs on a computer connected to a small radio. It receives supported MeshCore radio traffic, turns it into readable records, and saves those records locally. You can also add small scripts that respond to messages.

MeshCore is a radio-networking project that lets compatible devices exchange small messages without relying on the internet. KAM works alongside that network: it supplies computer-side storage and automation, while the connected radio handles sending and receiving over the air.

For example, a local radio group could run KAM on an always-on computer to keep a record of channel messages heard by its radio. Later, the operator could install a script that replies to a specific test message. Neither task requires a cloud database.

Purpose and longer-term direction

KAM's design is motivated by community communication when internet or mobile service is unavailable. Its longer-term direction includes operational bulletins, weather information, network-health reporting, and a shared message board. Those goals explain the architecture; they are not all available features.

CapabilityCurrent status

KAM is not a chat application, a replacement for radio firmware, or a repeater. Its saved history is not automatically a message board that other radios can retrieve.

Use as a supporting tool. Radio messages can be missed, and KAM cannot guarantee delivery or a complete archive. Do not use it as your only emergency communication method.

MeshCore Basics

Four different parts

  • Host computer: the computer running KAM. It provides processing, disk storage, and power for the software.
  • Radio hardware: the physical board and antenna that send and receive radio signals.
  • Firmware: the software installed on the radio board. Its role determines how the board behaves.
  • KAM: the separate program on the host computer. It talks to the radio through a USB cable.

LoRa is the radio technology used by many MeshCore devices. It carries small amounts of data over the air. It is not Wi-Fi, mobile internet, or the same thing as LoRaWAN, a different networking system that can use LoRa radios.

A mesh and its roles

A node is a participating device. A mesh is a network in which some nodes can pass messages onward. A repeater relays radio packets, potentially reaching places the original sender cannot reach directly. Each relay step is a hop. Actual range depends on antennas, terrain, placement, radio settings, and interference.

A companion radio connects to a chat application. A room server offers a message board with its own login and message-sharing behavior. A KISS modem exposes radio packets to a host program such as KAM. These are different firmware roles, not interchangeable names.

KAM needs the KISS modem role. A supported board running ordinary companion firmware does not become a KAM modem just because it has USB. Check firmware and board compatibility before connecting it.

What the USB connection carries

A serial port is a connection that carries a stream of bytes between the computer and radio. The operating system gives it a name such as /dev/ttyUSB0. KISS, short for Keep It Simple, Stupid, is the protocol that packages packets and modem commands on this connection. The USB link is local; LoRa is the separate over-the-air link.

Announcements, channels, and rooms

An advert is a device announcement containing identity and other device information. KAM checks its digital signature, a cryptographic check that the announcement matches its signing identity. That check does not prove the device owner is trustworthy.

A channel is a shared-key group conversation, for example #public. A key is the value used to encrypt and decrypt its messages. KAM needs a compatible channel key to turn received group-text packets into readable text. A matching channel name alone is not enough when devices use an explicitly configured key.

A room is a message board hosted by a room server, not another name for a channel. KAM can host rooms: MeshCore apps log in with a password, post, and receive posts they missed. This is optional and configured separately in kam.yml; see the room-server manual. KAM does not provide a general direct-message inbox, and the channel history it saves is not shared through a room.

MeshCore radio traffic does not require an internet connection, but it does require powered devices and usable radio paths. Downloading KAM, installing build tools, or fetching dependencies can require internet access during setup.

Design Philosophy

Maker-friendly & Pragmatic

KAM is designed for enthusiasts. We believe in a down-to-earth approach: prioritizing ease of setup and maintenance so you can get your node online and start communicating. We favor pragmatism over overly strict design or extreme security hardening. It's a tool for the community, meant to be tinkered with and used to build something real.

Local first, with few moving parts

KAM is one Go program rather than a collection of separate services. Go is the programming language used to build it. SQLite is its embedded database: it keeps structured records in local files without requiring a separate database server. This makes deployment simpler and removes a cloud dependency from normal operation.

Keep receiving even when other work is slow

Reading radio traffic, saving records, and running scripts are separate jobs. Small waiting lists, called queues, let these jobs hand work to one another. Their size is limited so a burst of traffic cannot make memory use grow without bound.

This deliberately favors keeping the receiving path responsive over retaining every record. If a storage or automation queue fills up, work can be dropped rather than making radio processing wait indefinitely. A local database is useful history, not proof that every transmitted message arrived.

One owner for a constrained radio

KAM's radio manager is the only part that uses the serial connection. It coordinates commands and outgoing messages so scripts and other components cannot independently overwhelm the modem. This matters because the modem has limited space for pending work and cannot attach a unique request number to every response.

Make optional behavior replaceable

Starlark is a small Python-like scripting language. An operator can install a script to react to a decoded channel message without rebuilding KAM. Scripts run with restricted capabilities: they can reply through KAM, but do not have general access to files, the internet, or operating-system commands.

A script runs with fresh state for each message. A timeout limits how long it can run; a script that exceeds its limit is marked FROZEN and needs operator attention. Optional automation is kept separate from the core job of receiving and storing traffic.

Give settings and records clear homes

YAML is the readable, indentation-based format used by kam.yml. This file holds node, radio, and channel settings. SQLite holds received records and installed scripts. Keeping that distinction clear makes it easier to understand what to edit and what to back up.

A Message's Journey

Suppose someone sends a short message on a channel that KAM has been configured to read:

  1. The connected radio receives a MeshCore packet, either directly or after other devices have relayed it.
  2. The modem sends the packet over USB to KAM inside a KISS frame, the protocol's packet container.
  3. KAM recognizes a supported group-text packet and attempts to decrypt it using its enabled channel keys.
  4. A decoded message is queued for local storage. If signal information is available, KAM attaches it to the record.
  5. Enabled scripts receive the decoded message through a separate queue. A script may request a reply through the same radio manager.

Optional replies travel back through KAM and the USB modem to the radio network. Saving an incoming message, sending a reply, and another person receiving that reply are separate events; none automatically proves the others happened.

RSSI means received signal strength; SNR means signal-to-noise ratio, how the signal compares with background noise. These describe reception at the connected radio, not the quality of every hop or confirmation of delivery.

What You Need

  • A computer that can run KAM, with disk space for its growing database and a usable USB serial connection.
  • A compatible LoRa radio running MeshCore's kiss_modem firmware, with the correct antenna and a USB data cable.
  • Permission to access the serial port. Linux systems may require membership in a serial-access group; ask the computer administrator if access is denied.
  • The radio settings used by your local MeshCore group and any channel keys you are authorized to use.
  • For a source build, Go 1.25 or newer and a local copy of the KAM project. Initial dependency downloads may need internet access.
  • Another compatible MeshCore device or existing local traffic for a meaningful reception test.

Choose settings for your location. Radio frequency, power, and transmission rules vary by country and hardware. The project's example settings are not a universal legal preset. Confirm local requirements and attach the correct antenna before allowing transmissions.

First Setup

The commands below run in a terminal, the application where you enter text commands, on the computer connected to the radio. They assume macOS or Linux and that the terminal is already in the KAM project folder.

1. Build the program

Check that the installed Go version is at least 1.25, then build KAM:

go version
go build -o kam .

A successful build creates the kam executable in this folder. The build may print nothing when it succeeds. If it fails, resolve the reported toolchain or dependency error before continuing.

2. Make your own settings file

Copy the supplied configuration once, before editing it. If kam.local.yml already exists, keep that file instead of overwriting your settings.

cp kam.yml kam.local.yml

Open kam.local.yml in a text editor. YAML uses indentation to group settings; preserve spaces and do not use tabs. Review these values rather than accepting the example unchanged:

SettingMeaning and action
node_nameThe name KAM uses for outgoing channel texts. Choose a recognizable name; it is not proof of identity.
db_pathWhere KAM saves its SQLite database. With kam.db, the file is in the directory from which you run KAM.
radio.portThe serial device name assigned to this radio by your computer, not another device's example name.
radio.baudThe USB serial communication speed. The KISS protocol documents 115200 baud; match your modem.
radio.frequency_hzThe radio's tuning frequency in hertz. Match your local network and legal band.
radio.bandwidth_hz, spreading_factor, coding_rateLoRa signal settings. Bandwidth is the signal's frequency width; spreading factor and coding rate affect how data is encoded. Match the local network rather than guessing.
channelsThe channel names, key choices, and enabled states KAM uses to decode group messages.

On macOS, serial device names often begin with /dev/cu.; on Linux, common names include /dev/ttyUSB0 and /dev/ttyACM0. To list candidates, use the command for your operating system:

# macOS
find /dev -name 'cu.*'

# Linux
find /dev -name 'ttyUSB*' -o -name 'ttyACM*'

A listed port is only a candidate. Confirm which entry belongs to the connected radio, and close other applications that might already be using it.

3. Understand channel keys

key_strategy tells KAM how to obtain a channel's key. public is reserved for #public and uses its configured public key. derived calculates a key from the normalized channel name. explicit uses the key supplied in key_hex, a hexadecimal representation containing digits and letters a-f.

Use the same compatible key as the other devices on the channel. Public and name-derived keys should not be treated as private secrets. An explicitly shared secret can restrict who decrypts traffic, but everyone holding it belongs to the same trust group.

4. Start KAM and check reception

./kam -config kam.local.yml

KAM opens local storage, contacts the modem, applies radio settings, and prints startup information. It keeps running in this terminal; an occupied terminal is normal. A serial-port or modem error is not a successful start.

The modem's radio-settings readback is an echo of requested values, not independent proof that the radio chip accepted them. Test reception with a known compatible device. After sending one harmless message on a configured channel, check that KAM logged a decoded group text and that a record reached the database.

If the SQLite command-line tool is installed, run this query from a second terminal in the same folder while KAM is running. It reports the number of stored group-text records; it does not display a chat interface.

sqlite3 kam.db 'SELECT COUNT(*) FROM group_texts;'

Compare the count before and after your test and allow time for background writes. Use your actual database path if it differs. A count increase indicates stored messages, not necessarily only your test message on a busy network. No change calls for a check of radio settings, channel keys, and logs.

Everyday Operation

Receive first, automate second

Start with receiving and saving messages before installing scripts. The bundled ECHO example, which replies when mentioned, is not enabled automatically on a fresh installation. Follow the Starlark quick start when you are ready to add a responder. Use narrowly targeted triggers so replies do not create unnecessary radio traffic.

An API, or application programming interface, is a way for another program to ask KAM to perform a task. KAM serves one local REST API for everyday tasks: it manages scripts and provides status, recent packet events, channel history and read-only room data at 127.0.0.1:8766. This address is loopback: it points back to the same computer, not to every computer on your network. It is not a browser-based management dashboard.

Modem control and room-client removal remain planned. KAMmon is one possible local client; KAM keeps working independently. The backend API manual explains configuration, endpoints, history and the separation between room passwords and web logins. Managing scripts is covered in the Starlark manual.

Change settings deliberately

KAM watches the configuration file and applies valid channel changes while running. Invalid changes are rejected, leaving the last valid channel set active. Changes to radio settings, node name, or database path require a restart. When using the channel command, pass the same configuration file as the running process.

Stop cleanly and back up

Press Ctrl+C in KAM's terminal and let it finish. A clean stop lets pending storage batches be written before the database and radio connection close. This does not protect against a sudden power failure or earlier queue drops.

Back up both your settings file and database: one contains channel settings and keys; the other contains received records and scripts. SQLite may use extra -wal and -shm files while running, so copying only the database file during live writes is not a reliable backup method.

With the SQLite command-line tool installed, this command makes a consistent database backup while KAM is running. Run it from a second terminal and change the path if you configured a different database:

sqlite3 kam.db ".backup kam-backup.db"

Keep backups in a separate, protected location and verify that they can be restored. Back up kam.local.yml separately; the database backup does not include it.

Privacy and Limits

  • Public is public. The #public key is publicly known. Encryption with a public key shared by everyone is not confidential messaging.
  • Readable records stay readable on disk. KAM stores decoded message content. Protect the computer, database, configuration, and backups with operating-system access controls; channel encryption does not protect those files.
  • A sender label is not identity proof. A name in group text is not equivalent to a verified advert signature. Do not trust a sensitive instruction solely because a message uses a familiar name.
  • Local does not mean authenticated. The script-management API has no authentication. Keep it on loopback and do not publish it through a proxy or network tunnel. Only trusted users should access this computer.
  • Room passwords are plain text. Like channel keys, they are in kam.yml. A room's private identity key is a separate file in the rooms directory; back it up with the database.
  • Coverage and airtime are limited. Airtime is the time a transmission occupies the radio channel. Long messages and frequent automatic replies consume a shared resource and can interfere with other users.
  • A saved record is not a delivery receipt. KAM only records supported traffic its radio receives and successfully decodes. Interference, incompatible settings, unavailable keys, and full queues can leave gaps.
  • Plan for maintenance. The connected radio and computer both need power; database files grow with traffic. KAM does not currently provide an automatic reconnect after a lost serial connection.

The room-server manual explains how radios can log in to a message board hosted by KAM. It does not share this database over the mesh: only posts made in a room are stored there, separately from the channel history. Room passwords are plain text in kam.yml, like channel keys. Weather lookups and the future authenticated Remote API are outside the current release.

Troubleshooting

KAM cannot open the radio

Check the USB data cable, device name, serial-access permissions, and whether another application has the port open. Confirm that the radio runs KISS modem firmware. A powered board or visible USB port alone is not enough.

KAM starts but messages do not appear

Confirm that nearby devices use compatible frequency, bandwidth, spreading factor, and coding rate. Check that the channel is enabled and its key matches. Test with a known nearby sender, then inspect the terminal for decoding or storage errors. A quiet terminal may simply mean no supported packets are being received.

A script does not answer

First confirm that the incoming message was decoded. Then check that the script is installed, enabled, and in READY state. BROKEN means its saved source could not be compiled or validated; FROZEN means it exceeded its time limit. The automation troubleshooting section explains recovery.

The modem is unplugged or stops responding

KAM detects serial-link failures and stops the running node. Restore the connection and start KAM again; do not assume it has reconnected automatically. A firmware reset is different from an unplug: the periodic health check can notice a reset and attempt to reapply startup settings.

You need more diagnostic information

Stop the current process before restarting it with debug logging. Debug output is more detailed. Even normal startup logs can include channel keys, and logs can contain message data; redact keys and personal content before sharing them.

DEBUG=1 ./kam -config kam.local.yml

Report the error text, operating system, radio board, firmware role/version, and steps that reproduce the problem. Remove private channel keys and personal message content.
