Feature Manual

Starlark Automations

Extending KAM functionality with custom, safe, sandboxed scripts.

Implemented (v1) Only the weather capability is still planned. Design: docs/FeatureStarlark.md

Overview

Starlark Automation lets an operator write small scripts that react to events on the radio. In this release the only event is a decoded group text (a message on a channel KAM can decrypt). Instead of compiling new Go code each time a behaviour changes, you install or edit a Starlark script through the Local Management API, and the change takes effect without restarting KAM.

What is Starlark? Starlark is a small dialect of Python designed for configuration and automation. It is deterministic and has no built-in access to files, the network or the operating system, which is why it is safe to run operator-supplied code in-process.

Scripts are stored in the SQLite database (table automation_scripts), not in kam.yml. The former built-in ECHO responder is now just an example script (docs/examples/echo.star); a fresh install has no ECHO until you install it.

Quick Start

KAM must be running (the API starts with it). The example installs a script that answers ping on #public:

curl -s -X POST localhost:8766/scripts \
  -H 'Content-Type: application/json' \
  -d '{"script":{"id":"ping","name":"ping","enabled":true,
       "source":"def on_group_text(message):\n    if message[\"channel\"] == \"#public\" and \"ping\" in message[\"body\"] and message[\"sender\"] != \"kam\":\n        reply(message[\"channel\"], \"pong, %d hops\" % message[\"hop_count\"])\n"}}'

To install the bundled ECHO example, edit its three settings (CHANNELS, MENTION, NODE_NAME) and post it:

jq -n --rawfile source docs/examples/echo.star \
  '{script: {id: "echo", name: "echo", enabled: true, source: $source}}' \
  | curl -s -X POST localhost:8766/scripts -H 'Content-Type: application/json' -d @-
Do not forget "enabled": true. A script created without it is stored but never runs. The same applies to updates: PUT replaces the whole script, so leave out enabled and you disable it.

The Automation Lifecycle

Two independent settings decide whether a script runs: enabled (what the operator wants) and runtime_status (what KAM has detected). A script runs only when it is enabled and READY.

  • READY: The script compiled and has not misbehaved. It runs for each event if it is also enabled.
  • BROKEN: A stored script failed to compile or validate when KAM loaded it at startup (for example because the host function set changed). It is inactive and last_error holds the reason.
  • FROZEN: A run exceeded the script's timeout_ms (default 500). KAM stopped dispatching to it, saved the error and waits for an operator to recover it.

What changes the status

EventResult
Source fails to compile through the APIRequest rejected with 422. The previous version, if any, keeps running. The script never becomes BROKEN this way.
Stored script fails to compile at startupBROKEN, saved with last_error. KAM still starts and keeps receiving.

recoverRecompiles the stored source; on success status becomes READY and last_error is cleared. May also set a new timeout_ms.
Saving new sourceCompiles first, then stores it as READY with last_error cleared, and swaps it in.

BROKEN and FROZEN survive a restart; a successful compile alone never re-activates them.

Writing a Script

Every script defines one entry point, which KAM calls once per group text:

def on_group_text(message):
    ...

A script without a callable on_group_text is rejected. Each event gets a fresh interpreter state: the top level of the file runs again on every event, and nothing you assign survives to the next message. Treat every message as a brand-new interaction; there is no persistent storage for scripts.

The message dictionary

The argument is a read-only (frozen) dictionary:

FieldTypeMeaning
channelstringNormalised channel name: lowercase with a leading #, e.g. "#public".
senderstringSender name parsed from the message; may be empty.
bodystringThe text after the sender: prefix.
timestamp_unixintThe sender's own timestamp, Unix seconds.
hop_countintNumber of relays the packet passed through.
hop_stationslist of stringsHex-encoded identity hashes of the relays, in path order.
has_rx_metaboolTrue when the modem reported signal quality for this packet.
snr_quarter_dbintSignal-to-noise ratio in quarter-dB units (divide by 4 for dB). Meaningful only when has_rx_meta is true.
rssi_dbmintSignal strength in dBm. Meaningful only when has_rx_meta is true.
time_drift_secondsintAbsolute difference between the sender's timestamp and KAM's clock, in seconds. Never negative.

KAM waits up to 200 ms for the modem's signal report; if it does not arrive, the event is delivered with has_rx_meta false (and snr_quarter_db and rssi_dbm at 0).

Scripts only see messages from channels KAM can decrypt, i.e. channels that are enabled in kam.yml.

Language limits worth knowing

  • No while loops; use for over a range or collection.
  • if/for statements are only allowed inside functions, not at the top level of the file.
  • Global variables cannot be reassigned once defined.
  • load() is not available: a script is a single file.
  • Calling a name that is neither defined nor a host function is a compile error, so typos are caught when you save.

Example: reply to a mention

NODE_NAME = "kam"          # must match node_name in kam.yml

def on_group_text(message):
    if message["channel"] != "#test" or message["sender"] == NODE_NAME:
        return
    if "@kam" in message["body"]:
        reply(message["channel"], "hello %s" % (message["sender"] or "someone"))
Avoid reply loops. A repeater may relay KAM's own reply back to KAM. A script that answers every message on a channel, without ignoring its own node_name as sender, will then answer itself indefinitely and flood the channel. Always filter on the sender and require a trigger such as a mention. The bundled echo.star does both.

Capabilities (Host Functions)

Scripts cannot touch the network, the filesystem or the radio directly. They can only call the functions KAM predeclares. Anything else is an "undefined" compile error.

FunctionStatusWhat it does
reply(channel, text) Implemented Sends a group text to a channel (flood route).
gps_coordinates(text) Planned Would parse latitude/longitude from text. No I/O.
weather_forecast(lat, lon) Planned Would return a small normalised forecast from a KAM-configured provider. Scripts will not choose URLs.

How reply behaves

  • Channel: must be a channel configured and enabled in kam.yml. Names are normalised, so "Public" and "#public" are the same. An unknown channel raises an error that is logged.
  • Format: the message is sent as <node_name>: <text>. Text is trimmed, and the whole message is truncated to fit one radio packet (about 170 characters including the name prefix).
  • Queued, not delivered: reply returns once the packet is queued for transmission, within a best-effort 500 ms send budget that is also bounded by the script's own deadline. It does not wait for the radio, and there is no delivery confirmation.
  • Rapid replies: the modem holds one transmission at a time and KAM does not yet pace transmissions on the modem's TxDone event, so several replies in quick succession can lose the later ones. See the KISS Modem manual.
  • Scope: scripts cannot send raw frames or change radio settings; reply is the only way out.
Deadlines: every host function receives the script's remaining time budget. A function that overruns it freezes the script, so slow work can never stall the single worker for long.

Management via the Local Management API

Scripts are managed over HTTP at 127.0.0.1:8766 (the same loopback listener as the read-only data surfaces; the default is configurable with monitor.listen in kam.yml). The API is reachable only from the KAM machine and has no authentication: anyone who can log in to that machine can change scripts.

Rules for every request

  • The Host header must be a loopback name (localhost, 127.0.0.1, [::1]), otherwise 403.
  • POST and PUT need Content-Type: application/json, otherwise 415.
  • Unknown JSON fields are rejected with 400, so a misspelt field name is an error rather than silently ignored.
  • Revisions: each script has a revision that increases on every save. Updates, enable, disable, recover and delete must send the revision you last read; a stale value returns 409. Create uses 0 (or omits it). A freeze or BROKEN status change does not bump the revision.

Endpoints

Typical session

# 1. See what exists and read the current revision
curl -s localhost:8766/scripts

# 2. Check a change before saving it
curl -s -X POST localhost:8766/scripts/validate -H 'Content-Type: application/json' \
  -d '{"source":"def on_group_text(message):\n    pass\n"}'

# 3. Disable without deleting (revision 1)
curl -s -X POST localhost:8766/scripts/ping/disable -H 'Content-Type: application/json' \
  -d '{"expected_revision":1}'

# 4. A frozen script: recover it with a longer timeout
curl -s -X POST localhost:8766/scripts/ping/recover -H 'Content-Type: application/json' \
  -d '{"expected_revision":2,"timeout_ms":1000}'

Recovery fixes the status, not the cause. A script that froze because it is slow will freeze again unless you fix the source or raise timeout_ms.

Security & Sandboxing

Automation is powerful, so it is strictly isolated:

  • No network, filesystem or process control: scripts cannot make HTTP requests, open sockets, read or write files, run shell commands or start threads.
  • No hardware access: scripts cannot reach the KISS modem commands; the only outbound action is reply.
  • Immutable input: the message is a frozen copy; scripts cannot alter KAM's internal data.
  • Loopback only: the API binds to 127.0.0.1 and refuses to start on any other address. The Host and Content-Type checks stop web pages in a browser on the same machine from driving it (DNS rebinding and cross-site forms).
  • Trust model: one system administrator. There are no users, ownership or per-script permissions, and no limits on script count, source size or reply rate. The operator is responsible for the timeout_ms they choose; it has no maximum.
  • Treat incoming text as untrusted: body and sender come from the radio. Do not assume they are well-formed.
Backups: the database now holds your script source. Include it in backups: sqlite3 kam.db ".backup kam-backup.db" while running, or copy kam.db with its -wal and -shm files while KAM is stopped.

Technical Deep Dive

Intended for developers.

The Execution Worker

KAM subscribes one handler to decoded group texts. The handler copies the message and does a non-blocking put on a 128-event queue, so a slow script can never block packet routing. If the queue is full the event is dropped and logged.

A single worker takes events in order. For each event it snapshots the enabled READY scripts and runs them one after another, sorted by script id. Execution is therefore sequential and deterministic; scripts need no locking and cannot run in parallel.

Each run uses the already-compiled program held in memory with a new interpreter thread and the script's deadline. SQLite is not read per event; it is touched only at startup, on API changes and when a status becomes FROZEN or BROKEN.

On shutdown KAM stops the API and event intake, cancels the running script, drops any queued events (and logs how many), and only then stops the radio manager.

Storage Schema

Scripts live in the SQLite table automation_scripts:

script_id      TEXT PRIMARY KEY      -- stable identity, e.g. "echo"
name           TEXT NOT NULL UNIQUE  -- human-facing name
source         TEXT NOT NULL         -- Starlark source (not bytecode)
enabled        INTEGER 0/1           -- operator's desired state (default 0)
timeout_ms     INTEGER > 0           -- per-run budget (default 500)
runtime_status TEXT                  -- READY | BROKEN | FROZEN (default READY)
last_error     TEXT                  -- latest BROKEN/FROZEN reason; cleared on READY
revision       INTEGER               -- optimistic-concurrency counter
created_at     INTEGER               -- Unix seconds
updated_at     INTEGER               -- Unix seconds

Only the latest error is kept; there is no error history. Databases that ran the retired one-time ECHO migration still contain a builtin.echo row. It is an ordinary script that can be edited or deleted.

Adding a host function

All capabilities are registered in one table, hostFunctions in internal/automation/runtime.go. Compilation accepts only those names as predeclared, and every call receives the invocation context so it shares the script deadline. A new function that does I/O must honour that context, because Starlark's own step limits do not bound time spent inside Go code. Adding the planned weather capability means adding entries here.

Example Script (ECHO)

The full responder is docs/examples/echo.star. It matches only configured channels, ignores the node's own messages, requires @kam not to be followed by a word character, and replies with the hop count, SNR/RSSI (when present) and clock drift:

heard alice in 2 hops, SNR 7.25 dB, RSSI -64 dBm, drift 3s

Its replies are pinned by the test TestEchoExampleScript. Downgrade note: an older KAM binary still reads an echo: block in kam.yml; disable the echo script first or both would answer.
