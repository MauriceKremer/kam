Feature Manual

Starlark Automations

Extending KAM functionality with custom, safe, sandboxed scripts.

Implemented (v1) Includes the periodic-posts extension: timers, rest_get, room_post. Design: docs/FeatureStarlark.md, docs/FeatureStarlarkPeriodicPosts.md

Overview

Starlark Automation lets an operator write small scripts that react to events on the radio. A script can run in two ways: it is called with each decoded group text (a message on a channel KAM can decrypt), and it can declare a timer so KAM calls it on an interval, such as every 15 minutes. Instead of compiling new Go code each time a behaviour changes, you install or edit a Starlark script through the Local Management API, and the change takes effect without restarting KAM.

What is Starlark? Starlark is a small dialect of Python designed for configuration and automation. It is deterministic and has no built-in access to files, the network or the operating system, which is why it is safe to run operator-supplied code in-process.

Scripts are stored in the SQLite database (table automation_scripts), not in kam.yml. The former built-in ECHO responder is now just an example script (docs/examples/echo.star); a fresh install has no ECHO until you install it.

Figure 1. The path from radio and timers to your scripts. Grey boxes are outside KAM, and the dashed box holds scripts you install through the API. Group texts and timer fires share one bounded queue, and a single worker runs scripts one at a time.

Quick Start

KAM must be running (the API starts with it). The example installs a script that answers ping on #public:

curl -s -X POST localhost:8766/scripts \
  -H 'Content-Type: application/json' \
  -d '{"script":{"id":"ping","name":"ping","enabled":true,
       "source":"def on_group_text(message):\n    if message[\"channel\"] == \"#public\" and \"ping\" in message[\"body\"] and message[\"sender\"] != \"kam\":\n        reply(message[\"channel\"], \"pong, %d hops\" % message[\"hop_count\"])\n"}}'

To install the bundled ECHO example, edit its three settings (CHANNELS, MENTION, NODE_NAME) and post it:

jq -n --rawfile source docs/examples/echo.star \
  '{script: {id: "echo", name: "echo", enabled: true, source: $source}}' \
  | curl -s -X POST localhost:8766/scripts -H 'Content-Type: application/json' -d @-

For a timer-based script, install the bundled weather poster the same way. Edit its settings at the top of docs/examples/periodic.star (ROOM and API_URL with your own weather API key) and give it a longer timeout, because one HTTPS round trip can exceed the 500 ms default:

jq -n --rawfile source docs/examples/periodic.star \
  '{script: {id: "periodic", name: "periodic", enabled: true, timeout_ms: 30000, source: $source}}' \
  | curl -s -X POST localhost:8766/scripts -H 'Content-Type: application/json' -d @-

From then on KAM calls its on_timer every 15 minutes and posts one line like Emmen 4.9°C, feels 1.8°C, Clear, wind 14 km/h, humidity 80% (19:52) into the room. The Timers & Periodic Posts section explains the pieces.

Do not forget "enabled": true. A script created without it is stored but never runs. The same applies to updates: PUT replaces the whole script, so leave out enabled and you disable it.

The Automation Lifecycle

Two independent settings decide whether a script runs: enabled (what the operator wants) and runtime_status (what KAM has detected). A script runs only when it is enabled and READY.

  • READY: The script compiled and has not misbehaved. It runs for each event and timer fire if it is also enabled.
  • BROKEN: A stored script failed to compile or validate when KAM loaded it at startup (for example because the host function set changed). It is inactive and last_error holds the reason.
  • FROZEN: A run exceeded the script's timeout_ms (default 500). KAM stopped dispatching to it, saved the error and waits for an operator to recover it.

Figure 2. What happens to a script's status. Solid arrows are normal paths; dashed arrows are the operator's recover paths. A save that does not compile is rejected with 422 and changes nothing; a stored script that fails at startup is BROKEN. FROZEN and BROKEN return to READY only through recover or a new save.

What changes the status

EventResult
Source fails to compile through the APIRequest rejected with 422. The previous version, if any, keeps running. The script never becomes BROKEN this way.
Stored script fails to compile at startupBROKEN, saved with last_error. KAM still starts and keeps receiving.
Run exceeds timeout_msFROZEN immediately in memory, then saved. If saving fails, it is logged and the script stays frozen until restart.
Run raises another error (bad call, reply failure)Logged only. Status stays READY; the next event or timer fire runs normally and later scripts still run.
enable / disableChanges enabled only. A FROZEN or BROKEN script stays inactive.
recoverRecompiles the stored source; on success status becomes READY and last_error is cleared. May also set a new timeout_ms.
Saving new sourceCompiles first, then stores it as READY with last_error cleared, and swaps it in.

BROKEN and FROZEN survive a restart; a successful compile alone never re-activates them.

Writing a Script

A script defines one or both of these entry points, and declares a timer by setting an interval at the top of the file:

def on_group_text(message):   # called for each decoded group text
    ...

def on_timer(message):        # called every timer_interval_minutes
    ...

timer_interval_minutes = 15   # integer literal, at least 1; 0/absent = no timer

KAM rejects a script with neither entry point, and also rejects an incomplete timer: timer_interval_minutes without a callable on_timer(message) is an error, and so is on_timer without the interval. The interval must be a plain integer literal written directly in the source (not a calculation and not a variable), so a script cannot change its own schedule; a value below 1 is rejected at save time. The API reports the compiled value as the read-only timer_interval_minutes field, and a request's value for it is ignored.

Each event or timer fire gets a fresh interpreter state: the top level of the file runs again every time, and nothing you assign survives to the next event. Treat every call as a brand-new interaction; there is no persistent storage for scripts.

The message dictionary

Both entry points take the argument message, a read-only (frozen) dictionary. For a group text it holds the fields below:

FieldTypeMeaning
channelstringNormalised channel name: lowercase with a leading #, e.g. "#public".
senderstringSender name parsed from the message; may be empty.
bodystringThe text after the sender: prefix.
timestamp_unixintThe sender's own timestamp, Unix seconds.
hop_countintNumber of relays the packet passed through.
hop_stationslist of stringsHex-encoded identity hashes of the relays, in path order.
has_rx_metaboolTrue when the modem reported signal quality for this packet.
snr_quarter_dbintSignal-to-noise ratio in quarter-dB units (divide by 4 for dB). Meaningful only when has_rx_meta is true.
rssi_dbmintSignal strength in dBm. Meaningful only when has_rx_meta is true.
time_drift_secondsintAbsolute difference between the sender's timestamp and KAM's clock, in seconds. Never negative.

KAM waits up to 200 ms for the modem's signal report; if it does not arrive, the event is delivered with has_rx_meta false (and snr_quarter_db and rssi_dbm at 0).

Scripts only see messages from channels KAM can decrypt, i.e. channels that are enabled in kam.yml.

A timer fire gets a much smaller dictionary: message["timestamp_unix"] is the fire time in Unix seconds, and that is all. Use it with the time module to format a clock time, as the weather example does.

Language limits worth knowing

  • No while loops; use for over a range or collection.
  • if/for statements are only allowed inside functions, not at the top level of the file.
  • Global variables cannot be reassigned once defined, so each timer_interval_minutes = may appear once.
  • load() is not available: a script is a single file.
  • Percent formatting has no precision flags ("%.1f" is an error) and there is no round(); %s on a float prints its shortest form (4.9) and %d truncates a float (14.0 becomes 14).
  • Calling a name that is neither defined nor a host function is a compile error, so typos are caught when you save.

Example: reply to a mention

NODE_NAME = "kam"          # must match node_name in kam.yml

def on_group_text(message):
    if message["channel"] != "#test" or message["sender"] == NODE_NAME:
        return
    if "@kam" in message["body"]:
        reply(message["channel"], "hello %s" % (message["sender"] or "someone"))
Avoid reply loops. A repeater may relay KAM's own reply back to KAM. A script that answers every message on a channel, without ignoring its own node_name as sender, will then answer itself indefinitely and flood the channel. Always filter on the sender and require a trigger such as a mention. The bundled echo.star does both.

Capabilities (Host Functions)

Scripts cannot touch the filesystem or the radio directly, and they get no general internet access. They can only call the functions and modules KAM predeclares. Anything else is an "undefined" compile error.

CapabilityKindWhat it does
reply(channel, text) Function Sends a group text to a channel (flood route).
room_post(room_id, text) Function Writes one post into one of KAM's own rooms, as the room identity. Clients receive it like any other post.
rest_get(url, headers=...) Function Fetches an HTTP(S) URL and returns (body, status). The script picks the URL and its key.
json, time Modules json.decode/json.encode for API payloads; time.from_timestamp and .format for clock times.

How reply behaves

  • Channel: must be a channel configured and enabled in kam.yml. Names are normalised, so "Public" and "#public" are the same. An unknown channel raises an error that is logged.
  • Format: the message is sent as <node_name>: <text>. Text is trimmed, and the whole message is truncated to fit one radio packet (about 170 characters including the name prefix).
  • Queued, not delivered: reply returns once the packet is queued for transmission, within a best-effort 500 ms send budget that is also bounded by the script's own deadline. It does not wait for the radio, and there is no delivery confirmation.
  • Rapid replies: the modem holds one transmission at a time and KAM does not yet pace transmissions on the modem's TxDone event, so several replies in quick succession can lose the later ones. See the KISS Modem manual.
  • Scope: scripts cannot send raw frames or change radio settings. The ways out are the capabilities listed above.

How rest_get behaves

  • Return value: a tuple (body, status). A server error such as 404 or 503 is not a script error: you get the body and the status code and decide what to do. The weather example stays quiet when the status is not 200.
  • Deadlines: the request uses the script's remaining time budget as its deadline. A slow API therefore freezes a fast-failing script no longer than timeout_ms; give timer scripts that call APIs a generous timeout_ms (the example uses 30000).
  • Size cap: a response body larger than 1 MiB (1,048,576 bytes) is an error, not a silent cut — a truncated JSON document would still decode and produce wrong data.
  • Accepted URLs: http and https only. A URL with a username and password (https://user:pass@…) is rejected; put credentials in the URL's query string or headers, as your API expects. Redirects are followed.
  • Headers: pass the optional second argument as a dictionary of strings, e.g. rest_get(url, {"Authorization": "Bearer " + key}).

How room_post behaves

  • Room id: the id from the rooms: list in kam.yml (the example posts to "lobby"). An unknown room raises an error that is logged; it does not freeze the script.
  • Author: the post is stored as the room's own identity, so clients see it without a sender name — like a pinned note on the board. Text is truncated to 150 characters, the same as a client post.
  • Delivery: the post enters the room's normal backlog, so clients that log in later receive it too, and online clients get it pushed within seconds. If rooms are not running (kam.yml has no rooms: list), the call errors instead of posting.
Deadlines: every host function receives the script's remaining time budget. A function that overruns it freezes the script, so slow work can never stall the single worker for long.

Timers & Periodic Posts

The second entry point lets a script act on its own schedule instead of waiting for radio traffic. KAM runs one timer loop for all scripts: each interval it checks which timer scripts are due and calls their on_timer(message), one script at a time through the same worker as group texts.

timer_interval_minutes = 15

def on_timer(message):
    room_post("lobby", "checkpoint at %s" % time.from_timestamp(message["timestamp_unix"]).format("15:04"))

What to expect:

  • First fire: about one interval after the script becomes enabled and READY — a 15-minute timer does not fire immediately after saving.
  • Changing the interval: saving a script with a new value restarts its cycle from that moment. Disabling, freezing or deleting the script removes it from the schedule; a recover or new save joins it again.
  • No catch-up: if one run is delayed (the worker is busy, KAM is restarting), the next fire is measured from when the previous one was due — you get steady pacing, never a burst of missed runs.
  • Counted with group texts: timer fires wait in the same 128-event queue; a full queue drops and logs a fire (timer fire dropped: queue full) rather than blocking anything.

The bundled docs/examples/periodic.star puts the pieces together — fetch, decode, format, post:

timer_interval_minutes = 15

ROOM = "lobby"
API_URL = "https://api.weatherapi.com/v1/current.json?key=YOUR_KEY&q=Emmen"

def on_timer(message):
    body, status = rest_get(API_URL)
    if status != 200:
        return  # stay quiet and try again next interval; a bad key is not room news
    weather = json.decode(body)
    current = weather["current"]
    text = "Emmen %s°C, feels %s°C, %s, wind %d km/h, humidity %d%% (%s)" % (
        current["temp_c"],
        current["feelslike_c"],
        current["condition"]["text"],
        current["wind_kph"],
        current["humidity"],
        time.from_timestamp(message["timestamp_unix"]).format("15:04"),
    )
    room_post(ROOM, text)

On the real WeatherAPI endpoint this posts one line such as Emmen 4.9°C, feels 1.8°C, Clear, wind 14 km/h, humidity 80% (19:52). Edit ROOM and API_URL (with your own API key) before installing; the Quick Start shows the command. The API key sits in the script source like a channel key in kam.yml — readable by anyone with database or API access, which on a single-operator node means you.

Management via the Local Management API

Scripts are managed over HTTP at 127.0.0.1:8766 (the same loopback listener as the monitoring API; the default is configurable with monitor.listen in kam.yml). The API is reachable only from the KAM machine and has no authentication: anyone who can log in to that machine can change scripts.

Rules for every request

  • The Host header must be a loopback name (localhost, 127.0.0.1, [::1]), otherwise 403.
  • POST and PUT need Content-Type: application/json, otherwise 415.
  • Unknown JSON fields are rejected with 400, so a misspelt field name is an error rather than silently ignored.
  • Revisions: each script has a revision that increases on every save. Updates, enable, disable, recover and delete must send the revision you last read; a stale value returns 409. Create uses 0 (or omits it). A freeze or BROKEN status change does not bump the revision.

Endpoints

RequestPurposeSuccess
GET /scriptsList all scripts with status, last_error and the read-only timer_interval_minutes.200
GET /scripts/{id}Read one script.200 (404 if unknown)
POST /scripts/validateCompile source without saving. Body: {"id", "source", "timeout_ms"}.200 {"valid":true} (422 with the compile error)
POST /scriptsCreate. Body: {"script": {...}}. id, name and source are required; timeout_ms defaults to 500; enabled defaults to false.201 (409 if the id or name exists)
PUT /scripts/{id}Replace the whole script. Body: {"script": {...}, "expected_revision": N}. Send enabled and a positive timeout_ms every time.200 (409 stale or name taken)
POST /scripts/{id}/enable
POST /scripts/{id}/disable		Change the desired state only. Body: {"expected_revision": N}.200
POST /scripts/{id}/recoverRecompile and return to READY. Body: {"expected_revision": N, "timeout_ms": M}; timeout_ms is optional.200 (422 if the source still fails)
DELETE /scripts/{id}?revision=NDelete the script. The ECHO script is not protected and is never recreated.204

Typical session

# 1. See what exists and read the current revision
curl -s localhost:8766/scripts

# 2. Check a change before saving it
curl -s -X POST localhost:8766/scripts/validate -H 'Content-Type: application/json' \
  -d '{"source":"def on_group_text(message):\n    pass\n"}'

# 3. Disable without deleting (revision 1)
curl -s -X POST localhost:8766/scripts/ping/disable -H 'Content-Type: application/json' \
  -d '{"expected_revision":1}'

# 4. A frozen script: recover it with a longer timeout
curl -s -X POST localhost:8766/scripts/ping/recover -H 'Content-Type: application/json' \
  -d '{"expected_revision":2,"timeout_ms":1000}'

Recovery fixes the status, not the cause. A script that froze because it is slow will freeze again unless you fix the source or raise timeout_ms.

Security & Sandboxing

Automation is powerful, so it is strictly isolated:

  • No filesystem, sockets or process control: scripts cannot open sockets, read or write files, run shell commands or start threads. The only network access is rest_get: plain HTTP(S) get requests the script's own source defines — there is no arbitrary port, protocol or file access.
  • No hardware access: scripts cannot reach the KISS modem commands. Outbound actions are limited to reply, room_post and rest_get.
  • Immutable input: the message is a frozen copy; scripts cannot alter KAM's internal data.
  • Loopback only: the API binds to 127.0.0.1 and refuses to start on any other address. The Host and Content-Type checks stop web pages in a browser on the same machine from driving it (DNS rebinding and cross-site forms).
  • Trust model: one system administrator. There are no users, ownership or per-script permissions, and no limits on script count, source size or reply rate. The operator is responsible for the timeout_ms they choose; it has no maximum.
  • Treat incoming text as untrusted: body and sender come from the radio. Do not assume they are well-formed.
  • Treat HTTP bodies as untrusted too: a rest_get body comes from the network you asked. json.decode throws on malformed input, so wrap the parse in your own expectations; never format a fetched string straight into a room post without looking at it.
Backups: the database now holds your script source. Include it in backups: sqlite3 kam.db ".backup kam-backup.db" while running, or copy kam.db with its -wal and -shm files while KAM is stopped.

Technical Deep Dive

Intended for developers.

The Execution Worker

KAM subscribes one handler to decoded group texts. The handler copies the message and does a non-blocking put on a 128-event queue, so a slow script can never block packet routing. If the queue is full the event is dropped and logged. A separate timer loop goroutine feeds the same queue: per script it keeps one next-fire time, recomputed after every wake from the compiled intervals; a change (save, enable, recover, delete) nudges it through a one-slot channel. Both event kinds are structs on the same channel, so the queue, drops and shutdown handling stay one mechanism.

A single worker takes events in order. For each event or timer fire it snapshots the enabled READY scripts and runs them one after another, sorted by script id. A timer fire re-checks eligibility and calls on_timer(message) with a one-key dictionary holding timestamp_unix. Execution is therefore sequential and deterministic; scripts need no locking and cannot run in parallel.

Each run uses the already-compiled program held in memory with a new interpreter thread and the script's deadline. The interval itself is fixed at compile time (the parser rejects anything but an integer literal of at least 1), so the schedule needs no recomputation between saves. SQLite is not read per event; it is touched only at startup, on API changes and when a status becomes FROZEN or BROKEN.

On shutdown KAM stops the API and event intake, cancels the running script, stops the timer loop first so no new fire can be queued, drops any queued events (and logs how many), and only then stops the radio manager and rooms.

Storage Schema

Scripts live in the SQLite table automation_scripts:

script_id      TEXT PRIMARY KEY      -- stable identity, e.g. "echo"
name           TEXT NOT NULL UNIQUE  -- human-facing name
source         TEXT NOT NULL         -- Starlark source (not bytecode)
enabled        INTEGER 0/1           -- operator's desired state (default 0)
timeout_ms     INTEGER > 0           -- per-run budget (default 500)
runtime_status TEXT                  -- READY | BROKEN | FROZEN (default READY)
last_error     TEXT                  -- latest BROKEN/FROZEN reason; cleared on READY
revision       INTEGER               -- optimistic-concurrency counter
created_at     INTEGER               -- Unix seconds
updated_at     INTEGER               -- Unix seconds

Only the latest error is kept; there is no error history. Databases that ran the retired one-time ECHO migration still contain a builtin.echo row. It is an ordinary script that can be edited or deleted.

Adding a host function

All capabilities are registered in one table, hostFunctions in internal/automation/runtime.go; json and time are the pinned go.starlark.net library modules, predeclared beside them. Compilation accepts only those names as predeclared, and every call receives the invocation context so it shares the script deadline. A new function that does I/O must honour that context, because Starlark's own step limits do not bound time spent inside Go code — rest_get and room_post were added as entries there.

Timer scheduling invariants

timerLoop (in internal/automation/runtime.go) owns next[id] and holds no lock over it: the map is loop-local, recomputed from the scripts' snapshot on every pass. Newly seen ids are seeded at now + interval; ids gone from the schedule are dropped. On wake it enqueues each due fire as a non-blocking send and re-arms next[id] = fired + interval, where fired is the due time, not the completion time — that re-arm is what prevents catch-up bursts after a stall.

Eligibility is decided twice, on purpose: the loop reads the shared scripts map under its read lock and dispatch re-checks before invoking, because a save may have replaced the resident program between snapshot and run. The API's TimerIntervals() reports every declared interval regardless of status, so a frozen script still shows its period; only the schedule drops it.

Example Script (ECHO)

The full responder is docs/examples/echo.star. It matches only configured channels, ignores the node's own messages, requires @kam not to be followed by a word character, and replies with the hop count, SNR/RSSI (when present) and clock drift:

heard alice in 2 hops, SNR 7.25 dB, RSSI -64 dBm, drift 3s

Its replies are pinned by the test TestEchoExampleScript. Downgrade note: an older KAM binary still reads an echo: block in kam.yml; disable the echo script first or both would answer.

The timer example is docs/examples/periodic.star, pinned by TestPeriodicExamplePostsTheWeatherLine against a replayed real WeatherAPI payload (it asserts the exact posted line above) and by TestPeriodicExampleStaysQuietOnAFailedRequest (a 401 produces no post and no freeze). Its header comment tells the operator to save it with timeout_ms = 30000.
