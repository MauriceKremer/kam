KISS Modem Command Layer

An explanation of how KAM communicates with the MeshCore KISS radio modem.

Implemented Code is complete; real-radio smoke tests and timing measurements remain pending.

Overview

KAM does not talk to a radio chip. It talks to a MeshCore KISS modem: a small board running MeshCore's kiss_modem firmware that does the LoRa work and exposes a serial port. The KISS (Keep It Simple, Stupid) protocol carries two kinds of traffic over that port: radio packets, and a set of control commands (called SetHardware) for configuring and querying the modem.

Goal of the command layer: a safe, typed, validated Go API, so that callers never build raw frames, a bad radio setting is caught before it is sent, and the modem is not overwhelmed with simultaneous transmissions.
Scope. The typed Tier 1 commands, request tracking, modem error handling, TX pacing, startup checks, optional radio settings and link-health probe are implemented. Crypto/identity commands and modem reboot remain deferred. Hardware-specific limits and timing still need confirmation on a real board.

How it Works

KAM uses a few small cooperating pieces, each with one job:

  • Reader: reads bytes from the serial port, undoes the KISS escaping and hands complete frames to the router.
  • Router: parses radio packets and classifies modem responses, errors and unsolicited events.
  • Writer: prioritizes control frames and sends at most one data frame until TxDone, retry outcome or gate timeout.
  • Manager: owns the serial port, request slot, queues, event subscriptions and link-health signal.
  • Radio client: typed Go methods for Tier 1 commands; callers do not construct raw frames.
  • Sender: builds group-text packets (used by Starlark reply) and queues them for the writer.

The modem has no request IDs. Several commands share OK (0xF0), so KAM allows one request at a time. If a request times out, the next one must pass a Ping barrier before it is sent.

Protocol Reference

The serial link is 115200 baud, 8 data bits, no parity, 1 stop bit, no flow control. All multi-byte numbers are little-endian.

Framing

Every message is wrapped in a frame end byte: FEND (C0) | type | data | FEND. If C0 or the escape byte appears inside the data, it is replaced with a two-byte escape sequence so it cannot be mistaken for a frame boundary:

ByteNameIn data it becomes
C0FENDDB DC
DBFESCDB DD

The type byte is port<<4 | command. Only port 0 is used, and frames for other ports are ignored. The largest unescaped frame is 512 bytes. A signed value can happen to equal C0: an RSSI of -64 dBm is the byte C0 and travels as DB DC.

Standard KISS Commands (host to modem)

These are the classic KISS parameters. None gets a reply, and the modem ignores a frame whose data is empty. KAM applies TXDELAY, persistence, slot time and full-duplex settings when a csma block is configured; TXtail is available through the client but is not configurable because the reviewed firmware does not use it.

TypeNameDataDefaultDescription
0x00Dataraw packet, 1-255 bytes-The radio packet to transmit. The modem holds one pending transmission at a time.
0x01TXDELAY1 byte, 10 ms units50 (500 ms)Wait after the channel is clear before starting to transmit.
0x02Persistence1 byte, 0-25563CSMA: transmit when a random number 0-255 is at most this value.
0x03SlotTime1 byte, 10 ms units10 (100 ms)Wait before the next CSMA attempt.
0x04TXtail1 byte, 10 ms units0Stored by the modem but not used by its transmit logic in the firmware reviewed.
0x05FullDuplex1 byte0Non-zero skips CSMA and transmits after TXDELAY. Harmful on a half-duplex LoRa radio.
0xFFReturn--Ignored.

In the other direction, a frame of type 0x00 from the modem carries a received radio packet. It has no signal metadata; that arrives separately as RxMeta.

Commands

Control commands use type 0x06 (SetHardware) followed by a sub-command byte: FEND | 06 | sub | data | FEND. A reply is 06 | (sub | 0x80) | data, so GetRadio (0x0B) is answered with 0x8B. Commands that just succeed answer the generic OK (0xF0). A failure answers Error (0xF1) with a code. An unknown sub-command answers Error/UnknownCmd, which is how a newer KAM can discover an older firmware: the firmware's single version number cannot be used to detect features.

The modem offers 26 sub-commands. KAM implements the Tier 1 radio, power, signal-report and diagnostic commands; crypto/identity functions and Reboot remain deferred.

Note on verification: after SetRadio KAM reads the values back with GetRadio. This "echo check" confirms the modem received the command and stored the numbers. It does not prove the radio chip applied them (see Modem Quirks).
Safety rule: no Starlark function and no automation-reachable API exposes the radio client. Scripts can only send group texts through reply; they can never change radio settings.

Radio Settings

The radio parameters come from the radio: block of kam.yml and are pushed to the modem once at startup. Changing them requires a restart; the config file watcher only reloads channels.

kam.yml keyOn the wireMeshCore rangeValidation
frequency_hzuint32, Hz300-2500 MHzRange checked at load and send
bandwidth_hzuint32, Hz7.8-500 kHzRange checked at load and send
spreading_factoruint85-12Range checked at load and send
coding_rateuint85-8 (meaning 4/5 to 4/8)Range checked at load and send
tx_power_dbmoptional uint8, dBm1-22Range checked at load and send

The example kam.yml uses 869.618 MHz, 62.5 kHz, SF 7, CR 5. KAM validates the documented ranges before sending. The actual chip may accept less: the common SX1262 driver takes only 150-960 MHz and -9 to 22 dBm. KAM cannot tell which chip is attached, so it cannot check chip-specific limits, and the modem still answers OK to a value the chip rejects. Startup RSSI and noise-floor readings are diagnostic hints, not proof that the radio accepted the values.

You are responsible for choosing a frequency and power that is legal where you operate.

Events & Errors

The modem also sends frames on its own, without being asked.

Events

FrameMeaningKAM behavior
06 F8 result
TxDone		 Sent once for every data frame the modem accepted for transmission. 1 means the transmission succeeded, 0 that it failed. Published as a modem event and releases the TX gate; success/failure is counted.
06 F9 snr rssi
RxMeta		 Follows each received data frame. SNR is a signed byte in quarter-dB units (0x1D = 29 = +7.25 dB). RSSI is a signed byte in dBm. Enabled by default after every modem boot. Used. Attached to the pending group text, which is released after 200 ms if the frame does not arrive.

Error codes

A failed command or rejected transmission produces 06 F1 code:

CodeNameTypical cause
01InvalidLengthThe command payload was too short or too long.
02InvalidParamA value was out of range (for example GetRandom length).
03NoCallbackThe board does not provide that function (for example no temperature sensor, or no stats).
04MacFailedModem-side decryption failed its MAC check (crypto commands, deferred).
05UnknownCmdThe modem does not recognise the command. Typical of an older firmware.
06EncryptFailedModem-side encryption failed (crypto commands, deferred).
07TxBusyA second data frame arrived while one was still pending. It is also queued when the modem's output queue overflowed and dropped one of its own responses or events, so it can mean "your response was lost" rather than "busy".

A pending command receives a typed ModemError immediately. An unmatched TxBusy is published to event subscribers and sent to the TX gate; other unmatched modem errors are published as faults. NoCallback and UnknownCmd match ErrUnsupported.

Modem Quirks

These behaviours come from reading the firmware source. The protocol document does not state most of them, and they explain several design choices.

BehaviourWhat it means for you
SetRadio and SetTxPower answer OK after only a length check. The board code ignores the radio driver's return codes.OK means "received", not "applied".
GetRadio and GetTxPower return a stored copy of what the host last sent. It is all zeros after boot or reset until the host sets it.The read-back is an echo. A zero answer reveals that the modem has reset.
Only GetCurrentRssi, GetNoiseFloor, IsChannelBusy and GetStats read real hardware state.Use those for health checks.
OK is shared by SetRadio, SetTxPower and Reboot, and there are no request IDs.After a timeout, KAM sends a Ping barrier and discards frames until its Pong.
A data frame of 0 or more than 255 bytes is discarded with no Error and no TxDone.Check the length before writing, or a pacing gate would wait for a TxDone that never comes.
The noise floor is zeroed after start-up and after every automatic gain reset (every 30 s when idle).A noise floor of 0 means "not calibrated yet", not 0 dBm.
While transmitting, or while its output queue is backed up, the modem skips receiving.KAM must keep reading the serial port promptly or it loses inbound packets.
GetSensors with no sensors answers an empty 0x95; GetMCUTemp answers NoCallback when there is no reading.Both mean "unsupported", not a failure.
A modem reset clears the stored radio values, RxMeta setting and KISS parameters without telling the host.The 30-second probe detects zero or changed cached radio values and reapplies startup settings.

Startup

Implemented startup sequence

Startup has a 10-second overall budget and a one-second maximum per command. Steps 1, 3 and 7 are fatal; optional features warn and continue when unavailable.

StepCommandIf it fails
1PingFatal: "no KISS modem on <port>".
2GetVersion, GetDeviceNameWarn.
3SetRadioFatal.
4SetTxPower (only if tx_power_dbm is set)Warn.
5SetSignalReport(true) (makes sure RxMeta is on)Warn.
6CSMA settings, ending with a Ping round trip (only if a csma block is set)Warn.
7GetRadio, compared with step 3Fatal on a mismatch.
8GetCurrentRssi, GetNoiseFloor, GetAirtime(255)Logged. The airtime sets the transmit-gate timeout.

The whole startup has a 10-second budget; each request keeps its own 1-second timeout. A summary line logs the device name, firmware version, the radio values the modem echoed and the RSSI and noise-floor readings.

Optional configuration

Unset optional keys leave modem defaults untouched. Radio values are validated during YAML load and again by the typed client.

If a csma block is present, omitted numeric fields use the modem defaults: 500 ms TXDELAY, persistence 63 and 100 ms slot time. Explicit zeroes are preserved. Without the block, KAM sends no CSMA parameter frames.

radio:
  # existing: port, baud, frequency_hz, bandwidth_hz, spreading_factor, coding_rate
  tx_power_dbm: 17        # 1-22
  csma:
    txdelay_ms: 500       # multiples of 10, 0-2550
    persistence: 63       # 0-255
    slot_time_ms: 100     # multiples of 10, 0-2550
    full_duplex: false    # true bypasses CSMA; KAM will warn at startup

TXtail will not be a config key, because it appears to have no effect in the firmware.

Technical Deep Dive

This section is intended for developers and intermediate users who need to understand the implementation details.

Request slot and Ping barrier

The Manager serializes one in-flight request with a context-aware slot. The router delivers an expected response or typed Error through a buffered result channel. Control writes are context-aware and the writer prioritizes them over data.

After a timeout or cancellation, the next request sends Ping and the router drops frames until Pong. This prevents a late response from being assigned to the following request. Unmatched frames are counted and dropped.

Request tracking and the "Barrier" mechanism

The Manager and router own one in-flight request slot. A request records the response codes it accepts plus Error, and a buffered result channel. Taking the slot honours the caller's context. Control frames use a queue the writer prioritizes over data frames.

If a command times out, the link is marked unsynchronized and:

  1. The next request first sends a Ping.
  2. KAM drops every frame until the matching Pong (0x97) arrives.
  3. Only then does the new request go out, so a stale reply cannot be credited to it.
  4. If the Pong does not arrive within the caller's deadline, the request fails with "modem unresponsive".

The router uses this classification for a 0x06 frame:

FrameConditionAction
RxMetaalwaysAttach to the pending group text (as today).
TxDonealwaysPublish the event and release the transmit gate.
Pongbarrier activeEnd the barrier; drop the frame.
any otherbarrier activeDrop as stale.
Errora request is pendingDeliver the error to that request.
Errorno request pendingPublish as a TxBusy or fault event.
expected responsea request is pendingDeliver the payload.
anything else-Debug log, count, drop. Never blocks.
Transmission pacing (the TX gate)

To avoid TxBusy (KAM writing before the modem is ready), the writer sends at most one data frame at a time:

1. Reject a payload outside 1-255 bytes, with a log entry.
2. Write one data frame and wait for TxDone, or for the gate timeout.
3. If TxBusy arrives, wait for a TxDone if one comes; otherwise back off 500 ms and resend once.
4. A second TxBusy drops the frame and counts it. A gate timeout releases the gate, logs and counts it; the frame was already written, so it is not resent.

The gate timeout is txdelay + 10 × slot_time + 3 × airtime(255). KAM reads airtime through GetAirtime after SetRadio; if unavailable, the calculation uses a conservative 1000 ms airtime fallback. Actual timing still needs hardware measurement.

The retry may duplicate a frame the modem had actually sent. Receivers drop such duplicates by payload hash; a lost frame cannot be recovered. Manager.Counters() reports TX completion, busy, retry, timeout, rejected-length and unmatched-response counts.

Priorities, airtime budgets and fairness between senders are not part of this feature. They belong to the transmit scheduler built for the room server, which sits on top of this pacing: it hands the writer one frame at a time and learns that the modem is free from TxDone, or from a TxAbandoned event when the writer drops a frame after a second TxBusy or a gate timeout.

Link health

When the serial link is lost, Manager.Done() closes and Node.Run returns an error so a supervisor can restart KAM.

A probe every 30 seconds sends Ping and then GetRadio through the normal request slot. An all-zero or different cached value means the modem reset, so radio settings and diagnostics are reapplied. Three consecutive probe timeouts trigger the same fail-stop as a lost link.
