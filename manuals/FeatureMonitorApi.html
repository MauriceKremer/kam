Architecture & API Manual

KAM Backend API

How another program can monitor and control KAM without becoming part of its radio service.

Phases 1-2 implementedStatus, events, channel history and read-only room resources are available. Modem control, room-client removal and script testing remain planned; real-radio verification is pending.

Overview

An API, or application programming interface, lets one program ask another program for information or request a change. Phases 1-2 of KAM's backend API provide status, recent radio and room events, configured channels with message history, and read-only room summaries, clients and posts. Any local dashboard or command-line script can use the same API.

For example, KAMmon could ask, "Which packets arrived since my last request?" KAM would return a list. KAMmon would draw the chart and decide which of its signed-in web users may see the details.

KAM does the radio work. KAMmon provides the web interface. KAM remains an open system: it starts, receives, stores messages and runs scripts without KAMmon. It does not register KAMmon as a client, check whether KAMmon is alive, or wait for it to consume events.

Available now: one loopback listener on port 8766 serving the bounded event ring, status and event reads, channel list/history, room list/client/post reads, and script management (the old script API on port 8765 is retired; see FeatureUnifiedApi.md). Modem controls and room-client removal are still planned. The listener answers GET / with the routes it serves right now.

Concepts & Responsibilities

The host computer runs both Go programs. The separate radio board runs MeshCore KISS modem firmware. MeshCore is the mesh radio system; KISS (Keep It Simple, Stupid) is the serial protocol KAM uses to exchange packets and commands with that board. A serial port is the computer's byte-by-byte connection to the modem.

REST is a conventional way to organise requests over HTTP. A request such as GET /v1/rooms asks for a resource. The reply uses JSON, a text format containing named values and lists. The HTTP method says what the request does; the path identifies the resource.

ComponentResponsibility
KAMRadio connection, packet processing, channel decoding, room protocol, storage, automation, and validation of API requests.
KAMmonPages, web login, web-user permissions, filtering visible data, charts and its own short-term memory.
KISS modemRadio transmission and reception, signal measurements and modem command replies.
SQLiteKAM's local database for received records, room state and installed scripts. KAMmon never opens it directly.
YAML configurationReadable settings files: kam.yml belongs to KAM; kammon.yml belongs to KAMmon.

Two Different Kinds of Login

KAM's local REST API has no web accounts, passwords or tokens. Any local program can use every endpoint that is offered. KAMmon authenticates its own web users and checks their permissions before making a request.

A radio joining a MeshCore room is different. Existing room passwords and radio-side roles remain KAM's responsibility. The admin password grants the room admin role; the guest password grants read/write; the configured read-only fallback grants guest access. These rules do not grant or restrict REST access.

There is no new pinned-role system or room role-editing endpoint in this feature. The room-server manual explains the existing radio roles. KAMmon's web-user role does not change a radio's room role.

Installation

There is no separate API executable to install. The monitoring listener is part of KAM's Go process. KAMmon is a separate Go program and project.

For the current release, follow the KAM installation guide. To manage scripts today, use the Starlark quick start. Adding the configuration below to an older build does not give it the planned API.

Configuration

This optional block belongs in KAM's kam.yml. These defaults also apply when it is omitted. Setting enabled: false removes both the listener and event recorder. Monitoring settings are read at startup; restart KAM after changing them.

monitor:
  enabled: true
  listen: "127.0.0.1:8766"
  event_ring: 8192

Loopback means a connection within the same computer. The address 127.0.0.1 is loopback; it is not the computer's address on your home network. The listener accepts only loopback addresses and loopback HTTP Host headers.

AddressPurposeStatus
monitor.listen (default 127.0.0.1:8766)The unified local REST API; script management shares the listener instead of the retired port 8765.Implemented
127.0.0.1:8766Status, events, channels, rooms; later room-client removal and modem control.Phases 1-2 implemented

The event-ring capacity may be 256 to 65536 events. It is a count limit, not a guaranteed duration. A busy network fills the ring sooner than a quiet network.

KAMmon uses these local addresses. Browsers connect to KAMmon, not directly to KAM's API. KAMmon owns web authentication and any outward-facing HTTPS setup.

Usage & Goroutines

A goroutine is a lightweight Go task that runs alongside other tasks in the same process. It is not another program or another copy of KAM.

Yes: the HTTP server runs in its own goroutine. Go's net/http package also creates goroutines to handle connections and requests. There is no permanent application worker assigned to KAMmon and no subscription registered for each monitoring client.

Reading Data

  1. KAM records a small event when it hears or sends a packet.
  2. KAMmon asks the HTTP server for events after its last cursor.
  3. The handler copies a bounded page from the ring under a short lock.
  4. It releases the lock before converting the copy to JSON or writing to the network.
  5. KAMmon adds the events to its own memory and updates its charts.

A slow reader cannot hold the event-ring lock while the reply is sent. Recording still has a small lock cost; the requirement is short, measured overhead, not a promise that a lock never waits.

Requesting Changes

The HTTP handler does not take ownership of the radio or room state. It asks the existing owner to perform the operation: the room worker removes a client, the serialised radio-control path changes settings, and the automation runtime manages scripts.

Normal requests have a 5-second deadline, with at most eight monitor requests admitted at once. Extra requests receive a busy response. Modem apply/recovery has a longer bounded budget, explained below. Reads do not create another recording worker or a separate event queue.

When KAMmon Is Absent

KAM does not change its radio processing to accommodate an absent viewer. If no one reads the ring, the oldest events are replaced. If the API listener cannot start, KAM logs that failure and continues its normal work. If KAMmon stops, KAM does not wait for a disconnect message.

This isolates API failures; it does not make the hardware invulnerable. A real serial-link failure still follows KAM's existing fail-stop behavior, described in the KISS modem troubleshooting section.

Event History

The event ring is a fixed-size list in KAM's memory. Each event has a number, seq, and a time, at. A cursor is simply the last number the caller has received. An epoch is a new identifier created whenever KAM starts; it tells a client when sequence numbers have restarted.

Events carry packet type, route, lengths, signal measurements when available and estimated airtime. Room events also carry activity names and client keys. Events do not contain raw payload bytes or decoded message bodies. Message text is read separately through the channel and room history endpoints.

FieldPlain meaning
epochWhich run of KAM this reply belongs to.
first_seqOldest event still in KAM's ring.
last_seqNewest event KAM holds, whether or not it is in this page.
next_afterLast event delivered in this page. Use this for the next request.
resetThe epoch changed or earlier events were lost before the client read them.

The 5,000-Event Example

KAM holds events 1 to 5000 but returns only 1000 per request. The first response says last_seq: 5000 and next_after: 1000. KAMmon asks for events after 1000, not after 5000. That delivers the next page without skipping 4000 events.

The first request uses after=0 without an epoch. Subsequent requests use both the returned epoch and next_after. When caught up, an empty array is normal. If the ring is empty, all three sequence fields are zero.

KAMmon polls every one or two seconds. There is no permanent stream, broker, long-poll request or server-side client cursor. A restart or overwritten ring produces a visible history boundary or gap.

What Survives a Restart?

DataWhere it livesAfter restart
KAM event ringKAM memoryLost when KAM restarts; epoch changes.
KAMmon chartsKAMmon memoryLost when KAMmon restarts; it rebuilds from available ring events.
Messages, room state and scriptsKAM SQLite databaseExisting persistence rules apply; these are not a complete packet archive.

A 24-hour chart fills while KAMmon runs. It cannot promise 24 hours of history immediately after restart. Signal values are null when unknown, not zero. Airtime is an estimate, and repeated packets still occupied the channel.

Examples

Run these read commands in a terminal on the KAM computer while KAM is running. Channel and room reads are implemented; modem-query examples below remain planned. Automated tests verify phases 1-2; real-radio acceptance is still pending.

Ask KAM What It Serves

curl --fail-with-body http://127.0.0.1:8766/

Both listeners answer GET / with the routes each one serves, with a one-line purpose per route.

Read Status

curl --fail-with-body http://127.0.0.1:8766/v1/status

List endpoints have a named outer object. A channel-list response with no configured channels is:

{"channels": []}

Read a Page of Events

curl --fail-with-body 'http://127.0.0.1:8766/v1/events?after=0&limit=1000'

The following is a complete empty-ring response. The identifier is illustrative:

{
  "epoch": "7f3a9c2e41b8d605",
  "first_seq": 0,
  "last_seq": 0,
  "next_after": 0,
  "reset": false,
  "events": []
}

For a nonempty page, use the actual returned values in the next request. The shell variables below are placeholders to replace with that response:

EPOCH='replace-with-returned-epoch'
AFTER='replace-with-returned-next_after'
curl --fail-with-body "http://127.0.0.1:8766/v1/events?epoch=$EPOCH&after=$AFTER&limit=1000"

Read Channel Messages

The # in a channel name must be encoded as %23 in a URL; otherwise the browser treats it as a page fragment.

curl --fail-with-body 'http://127.0.0.1:8766/v1/channels/%23emmen/messages?limit=20'

If more records exist, use next_before_id as before_id for the next page. Message pages are newest first; event pages are oldest first.

Read Rooms

curl --fail-with-body http://127.0.0.1:8766/v1/rooms
curl --fail-with-body http://127.0.0.1:8766/v1/rooms/lobby/clients
curl --fail-with-body 'http://127.0.0.1:8766/v1/rooms/lobby/posts?limit=20'

Room lists include per-room counters and remembered-client totals. Client roles describe the existing radio login; they are not REST permissions. The room subsystem returns 503 when disabled.

Query a Signal Reading (Planned)

curl --fail-with-body -X POST http://127.0.0.1:8766/v1/modem/query \
  -H 'Content-Type: application/json' \
  -d '{"command":"GetCurrentRssi"}'

Illustrative response, with RSSI (received signal strength) in dBm:

{
  "command": "GetCurrentRssi",
  "at": "2026-10-11T15:00:00.000Z",
  "duration_ms": 8,
  "supported": true,
  "value": -106
}

If an apply request disconnects or times out, it may already have sent commands. Read GET /v1/modem and its last_change field before deciding what to do. A failed HTTP request does not prove that the modem stayed unchanged.

Endpoint Reference

Status, event, channel and read-only room endpoints on port 8766 are implemented. Room-client removal and modem controls remain planned. Both listeners answer GET / with the routes they serve, implemented ones only. GET reads data, POST requests an action, PUT applies a setting and DELETE removes a record. Paths beginning with /v1 identify version 1 of the contract.

Method & pathPurpose
GET /The routes this listener serves right now.
GET /v1/statusNode identity, uptime, link, radio echo, queue/counter summaries and event-ring bounds.
GET /v1/eventsBounded pages of recent packet and room events; script and modem events remain planned.
GET /v1/channelsConfigured names, key strategy, enabled state and retained message counts. Never keys.
GET /v1/channels/{name}/messagesDecoded text with paging and substring search.
GET /v1/roomsActive rooms, public identities, remembered clients, activity and counters.
GET /v1/rooms/{id}/clientsRadio-client keys, existing protocol roles, last activity, push state and optional advert labels.
GET /v1/rooms/{id}/postsNewest retained posts and authors.
DELETE /v1/rooms/{id}/clients/{key}Forget a session and cancel its pending pushes. This does not ban the radio.
GET /v1/modemCached diagnostics; does not send a modem command on each read.
POST /v1/modem/queryOne typed read-only modem command.
PUT /v1/modem/radio?preview=trueValidate and list intended commands without sending or saving.
PUT /v1/modem/radioApply, check echo, save and recover on failure.

Use actual ids and public keys in paths, not the braces shown in the table. Room keys are 64 lowercase hexadecimal characters. Times use RFC 3339 UTC timestamps. Unknown measurements are null; empty lists are [].

Removing a room client deletes its session, not its credentials. It may log in again under the existing room rules. No endpoint in this feature changes a radio client's role or edits KAMmon's web users.

Modem Changes

Planned behavior: KAMmon asks KAM to perform the change; KAMmon never writes raw KISS frames. The serial port and baud rate cannot be changed here. Frequency, bandwidth, spreading factor and coding rate are required; transmit power and a complete CSMA object are optional.

CSMA (carrier-sense multiple access) is the modem's wait-and-retry behavior before transmitting. LoRa is the long-range radio modulation; its frequency, bandwidth, spreading factor and coding rate must match your network. Choose legal settings for your hardware and region, not merely numbers inside an API range.

  1. Validate all requested values and take the single radio-change gate.
  2. Pause new transmissions, retain queued packets, and wait for the active transmission to finish. Suspend reset-probe and diagnostic work during the change; continue receiving.
  3. Send the typed commands and compare the modem's cached radio and power echo. Keep signal reporting enabled.
  4. Check that kam.yml has not changed, then save atomically with the existing writer.
  5. Update runtime defaults used by the reset probe, airtime estimator and scheduler, then resume transmission.
  6. On any failure after changing the modem, try restoring previous settings, including when saving the file fails.

Echo is not hardware verification. The modem may acknowledge settings its radio chip rejected. A matching readback confirms the modem stored the requested numbers, not that reception or transmission works with them. CSMA setting commands have no individual replies.

If restoration succeeds, transmission resumes. If restoration fails, KAM keeps transmission paused, continues receiving and reports uncertain modem state. A later successful explicit apply or successful startup reapplication clears that pause. This recovery does not guarantee continued reception if the radio hardware or serial link has itself failed.

Apply has up to 10 seconds for waiting, changing and saving, plus a maximum 5 seconds for recovery. Recovery can finish even if the caller disconnects. The caller keeps no asynchronous job in KAM; the snapshot contains only the latest operation outcome.

Saving uses KAM's existing YAML writer, which rewrites the file and drops comments, just like channel upserts. Signal reporting is always enabled and is not an editable setting.

Script Testing

Starlark is the restricted scripting language KAM uses for automation. Script management shares the unified listener on port 8766 with the monitoring surfaces, keeping its current revision checks. The planned additions are in-memory last-run information and POST /scripts/dry-run.

A dry run compiles and runs supplied source against a fixture, a made-up input message. Calls to reply(channel, text) are captured as output instead of being transmitted. The test does not save the script, change its enabled state or freeze the live version.

Test limitMeaning
500 ms default; 3000 ms maximumCompilation and execution are bounded. This does not change a live script's configured timeout.
One test at a timeA concurrent test gets 409; no job queue is added.
16 replies, 4096 UTF-8 bytesMaximum captured output across channel names and reply text. Exceeding either stops the test with an error.
ok: false with HTTP 200The test completed but the script failed. Inspect its error and captured replies.

The input must name an enabled channel. Defaults include sender test, empty body, zero hops and no signal metadata. A disconnected caller cancels the test. Successful or failed dry runs never update live execution statistics.

Read the Starlark manual for the current message dictionary and reply behavior. Run statistics reset when KAM restarts; they are not a permanent execution log.
