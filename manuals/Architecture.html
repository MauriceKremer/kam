Architecture

See every part of KAM in one layered map, then follow a message through it.

ImplementedDescribes the code as it stands on 6 November 2026. Room servers are implemented; the Room Server manual tracks their hardware verification.

How to Read This Page

KAM is one program that runs on your computer. It listens to a MeshCore radio, saves what it hears in a database, runs your scripts, and can host room servers. Inside, it is split into small parts. Each part does one job and hands its result to the next part.

This page draws those parts as layers. Higher layers use lower layers; a lower layer never needs to know what is above it. That is why a broken script or room cannot stop the radio from receiving.

What the diagram's shapes mean

  • Solid outline: always running while KAM runs.
  • Dashed outline: optional. KAM starts it on a best-effort basis; if it fails to start, KAM logs the problem and keeps receiving.
  • Grey fill: outside KAM, such as the radio, a file, or a person.
  • Arrows: the direction data travels. A label names the hand-off.
  • Blue: the journey you picked with the buttons above the diagram (needs JavaScript). The same journeys are written out as numbered steps further down.

Words used on this page

TermMeaning
KISS modemA small radio board that passes raw radio packets to the computer over a USB serial cable. KISS is the simple framing protocol it speaks.
Packet and frameA packet is one MeshCore radio message. A frame is the packet wrapped for the serial cable.
LoopA task that repeats forever, such as "read bytes from the cable". Each loop runs in its own goroutine, Go's lightweight thread.
QueueA waiting line with a fixed size. When a queue is full, KAM drops the newest item and counts it instead of freezing the radio.
TapA hook where another part asks to be told about every packet or message of one kind. The router calls the hook and does not know who is listening.
AdvertA MeshCore announcement in which a node says who it is.
Group textAn encrypted message sent to a channel. KAM can read it only if you configured that channel's key.
Room serverA message board that MeshCore apps log in to. See the Room Server manual.
StarlarkThe small scripting language KAM uses for automations. See the Starlark manual.

Follow One Journey

Each journey below matches a button above the diagram. The steps use the names printed in the boxes, so you can trace them on the map.

A group text is received

Example: someone sends "test" on a channel you configured.

  1. The radio hears the packet and sends it to KAM as a KISS frame over the USB serial cable.
  2. The reader loop turns the incoming bytes into whole frames and puts each one on a ten-slot queue for the route loop.
  3. The route loop reads the packet header and drops the packet if it saw the same one recently, because mesh networks repeat packets.
  4. It sorts the packet by type. A group text goes to the parsers, which decrypt it with the channel keys loaded from kam.yml. An advert goes to the same place and has its signature checked.
  5. The modem sends signal-quality numbers (SNR and RSSI) in a separate frame just after each packet. The route loop holds the decoded message for up to 200 ms to attach them, then moves on even if they never arrive.
  6. The message is queued for SQLite, where a background writer saves it. Every group-text subscriber is then called. Automation is one subscriber: it copies the message into its own 128-slot queue.
  7. The automation worker runs your enabled scripts against the message. Timer scripts are not part of this flow: a timer loop calls them on their declared interval through the same 128-slot queue.

A room packet is received

Example: a MeshCore app logs in to your room and posts "hello".

  1. The radio, the reader loop and the duplicate check work exactly as in steps 1 to 3 of the group-text journey above.
  2. The route loop sees a peer packet type (REQ, TXT_MSG, ACK, ANON_REQ, PATH or MULTIPART) and calls every packet-tap subscriber. The room server is the subscriber.
  3. The room service puts the packet in a 64-slot queue and returns immediately.
  4. The room worker takes the packet, works out which room and client it belongs to, and handles it.
  5. A post is saved to SQLite and flushed to disk before KAM queues the acknowledgement.
  6. The acknowledgement goes to the transmit scheduler, then out through the writer loop.

The next section zooms in on steps 2 to 4.

A reply is sent

Example: a script answers "test" with "received".

  1. The script calls reply(channel, text). Automation passes it to the sender.
  2. The sender builds an encrypted group-text packet and submits it to the transmit scheduler. A room submits its own packets the same way.
  3. The scheduler orders waiting packets by priority and keeps pushes and adverts inside an airtime budget, so one busy source cannot hog the radio.
  4. It hands one packet at a time to the writer loop, and notes the packet as sent by KAM so a repeater's echo is dropped as a duplicate instead of being processed again.
  5. The writer loop wraps the packet in a KISS frame, writes it to the serial port and waits for the modem's TxDone signal. Only then does the scheduler release the next packet.

Settings change

Example: you run kam channel upsert to add a channel.

  1. The command runs as a short separate process. It asks internal/config to add the channel to kam.yml, replacing the file atomically.
  2. The running KAM checks kam.yml every 500 ms.
  3. When the file changes, KAM validates it. If it is invalid, KAM keeps the last good settings.
  4. If it is valid, KAM builds a new channel registry and swaps it in. The parsers use it for the next packet. No restart is needed.

A REST request

Example: an operator tool asks for recent events.

  1. The tool sends an HTTP request to 127.0.0.1:8766, the default address. The API listens on the local machine only.
  2. internal/api checks the request, runs at most eight at once, applies a five-second limit and decodes any JSON body.
  3. The API never touches the radio or the database directly. It calls small adapters that internal/node supplies for status, events, channels, rooms and scripts.
  4. The adapters read the bounded event ring, the channel registry, the room service or the script repository, and the API sends back JSON.

The Backend API manual lists every endpoint.

How the Room Server Receives Packets

The route loop never calls the room server by name. It only knows a packet tap: a list of functions to call when a room-type packet arrives. When KAM starts, internal/node adds the room service's HandlePacket function to that list. That is the entire connection between the two.

Two rules keep the radio safe. The tap function runs on the route loop's own goroutine, so it must return at once. And the room server does its real work on a separate goroutine, which it feeds from a small queue.

Figure 2. A packet's trip to the room server and the acknowledgement's trip back. Solid arrows are calls or hand-offs; dashed arrows are returns or later effects.

The steps

StepWhat happensSource
1–2The reader loop assembles a KISS frame and puts it on the route loop's queue.kiss_reader.go
3The route loop decodes the packet, drops duplicates, and picks a path by payload type. Adverts and group texts keep their own paths. Six peer types go to the packet tap.kiss_router.go
4The tap copies its list of handlers and calls each one on the route loop's goroutine.kiss_manager.go
5–6HandlePacket tries to put the packet on a 64-slot channel. If the channel is full it counts a dropped packet and returns anyway.service.go
7The worker goroutine takes one packet at a time and handles it by type. It also wakes every 50 ms for time-driven work.service.go, room.go
8–9A post is stored with a full disk sync before anything else happens.rooms.go
10–11The acknowledgement goes to the shared transmit scheduler, which sends it out when its turn comes.send.go, scheduler.go

The wiring in code

The node subscribes the room service after it starts it, in node.go:

service.Start()
unsubscribePackets = manager.SubscribePackets(service.HandlePacket)

The router sends the six peer packet types to the tap, in kiss_router.go:

case PAYLOAD_TYPE_REQ, PAYLOAD_TYPE_TXT_MSG, PAYLOAD_TYPE_ACK, PAYLOAD_TYPE_ANON_REQ, PAYLOAD_TYPE_PATH, PAYLOAD_TYPE_MULTIPART:
    m.dispatchPacket(RxPacket{Packet: pkt, ReceivedAt: time.Now()})

The room service queues without ever waiting, in service.go:

func (s *Service) HandlePacket(pkt kiss.RxPacket) {
	select {
	case s.in <- pkt:
	default:
		s.cnt.packetsDropped.Add(1)
	}
}

Why it is built this way

  • Rooms stay optional. The kiss package does not import room; the room package imports kiss. The router only knows a function type, so KAM works with no rooms configured, and a room that fails to start never stops the radio.
  • A slow room cannot stall reception. Saving to SQLite takes disk time. The route loop never waits for it, because the tap only drops a packet into a queue.
  • No locking on room state. One worker owns every room, client list and push cursor. Nothing else reads or writes them.
  • Overload loses packets, not control. A full queue drops the newest packet and counts it, so a burst costs a lost packet rather than a frozen radio. KAM cannot guarantee that every packet is delivered.
  • Duplicates never reach the room. The duplicate check runs before the tap, so a packet heard through two repeaters is handled once.

What the worker does with each packet type

TypeMeaningWhat the room does
ANON_REQA login from a client the room does not know yet.Applies the login rate limit, finds the room by its address byte, decrypts, checks the password, and answers.
TXT_MSGA post from a known client.Saves the post, then queues the acknowledgement. A repeated timestamp is treated as a retry and acknowledged again.
REQA request from a known client.Answers keep-alives sent on a direct route. Other request types are counted and get no reply.
PATHThe route a client found back to the room.Remembers the route for later pushes. It may also carry an acknowledgement.
ACK, MULTIPARTA client confirms it received a pushed post.Matches the acknowledgement to the waiting push and moves that client's sync cursor on. Only acknowledgements inside a MULTIPART packet are used.

Before handling anything, the worker skips a direct packet that still has hops left. That packet is meant for a forwarder, not for its final destination. A packet that is not addressed to a room is dropped without a reply.

Where the group-text tap differs. Automation is wired the same way, through SubscribeGroupText, but its tap fires after the 200 ms signal-quality wait and after the message is queued for SQLite. See A group text is received.

Queues and Priorities

Every hand-off between two parts goes through a waiting line of fixed size. Fixed sizes mean a burst of radio traffic cannot make KAM run out of memory or freeze. When a line is full, KAM sheds load in a known way instead.

Hand-offSizeWhen it is full
Reader loop to route loop10 framesThe reader waits, so reading slows down.
Route loop to SQLite (adverts, group texts)Bounded queues with batched writesNew records are dropped and counted.
Route loop to automation128 messages (group texts and timer fires share the queue)The message is dropped, a warning is logged and a counter goes up.
Route loop to room server64 packetsThe packet is dropped and a counter goes up.
Senders and rooms to transmit scheduler128 packetsPushes and adverts are evicted first. If nothing can be evicted the submit fails.
Transmit scheduler to radioOne frame in flightThe scheduler waits for TxDone. If it never comes, the writer gives up after a timeout and the scheduler moves on.

Who goes first on the air

All outgoing packets share one radio, so the transmit scheduler sends the lowest-numbered priority first. Pushes and adverts are the ones allowed to wait when the airtime budget is spent, so they cannot crowd out the answers people are waiting for.

0ReplyAcknowledgements and direct replies a client is waiting on.No

Start-up and Shutdown

internal/node builds the parts in an order where each part only uses things that already exist. It stops them in nearly the reverse order, so nothing is closed while another part still needs it.

Start-up order

  1. Load the channel keys from kam.yml into the parser registry.
  2. Open SQLite and start the advert and group-text writers.
  3. Open the serial port and start the reader, writer and route loops.
  4. Ping the modem, then set and verify the radio settings. Without a working modem, start-up fails and KAM exits.
  5. Create and start the transmit scheduler and the sender.
  6. Optional: start the room servers and subscribe them to the packet tap.
  7. Optional: load the scripts, start automation and subscribe it to the group-text tap.
  8. Optional: start the local REST API.

An invalid room is switched off with a log message, not a crash. A room or automation start-up failure never stops radio reception.

Shutdown order

  1. Stop the radio health probe and the settings watcher.
  2. Shut down the REST API, waiting up to five seconds.
  3. Unsubscribe automation and the room server from their taps, so no new work arrives.
  4. Stop automation, then close its script repository.
  5. Stop the room server, which saves its client state, then close the room repository.
  6. Stop the transmit scheduler.
  7. Stop the KISS manager. It flushes the queued SQLite writes and closes the database and the serial port.

Stop KAM with Ctrl-C or SIGTERM. That runs the shutdown order above and saves queued records. Killing the process forcibly can lose records still waiting in queues.
